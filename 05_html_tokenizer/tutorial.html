State Machines

The Big Analogy

🍽️ The Restaurant, continued

The prep cook opening the crate doesn't read the packing slip as one giant sentence. They read it item by item, and — critically — their current mode changes what a symbol means. A quotation mark seen while reading "ingredient name" mode means something different than one seen while already inside a quoted note. And if the slip includes a photocopied recipe card taped inside it (a `<script>` block), the prep cook doesn't try to treat the recipe's own punctuation as more packing-slip instructions — they read the whole recipe as one attached note and move on once they find its edge.

What Happens, Step by Step

  1. Start in the DATA state, accumulating plain characters into a text buffer.
  2. See a <: flush any buffered text as a Text token, then look at what follows to decide what kind of markup this is.
  3. <!-- → scan for the matching --> and emit one Comment token, whatever's inside it (even fake-looking tags).
  4. </ → read a tag name and emit an EndTag token.
  5. A letter → read a tag name, then loop reading attribute name/value pairs (handling double-quoted, single-quoted, and unquoted values differently) until > or />, and emit a StartTag token.
  6. If that start tag was <script> or <style>, switch to RAWTEXT state: everything until the matching end tag is one literal Text token, < and > included, no exceptions.

A Map of the States

see '<' see letter DATA ───────────────► (peek) ───────────────► consume start tag ──► emit StartTag ▲ │ │ │ text char │ see '/' │ name in {script, style}? │ (buffer it) ▼ ▼ │ consume end tag RAWTEXT (scan for ' ─► emit Comment ─► back to DATA

DATA and RAWTEXT are the only two states that change what counts as markup at all

Limits / What You Cannot Do Yet

Can't do yet

  • Decode entities — &amp; stays as four literal characters, not &
  • Build any tree structure — tokens are still a flat list
  • Recover from deeply malformed HTML the way real browsers famously do (Module 6)

Can do now

  • Correctly tokenize tags, attributes (all three quoting styles), comments, and self-closing tags
  • Correctly protect script/style content from being misread as markup
  • Correctly order text relative to the tags around it

Brain Exercise

🧠 Think before you reveal

The very first version of this tokenizer flushed buffered text before emitting a StartTag token, but NOT before an EndTag or Comment token. Before reading DECISIONS.md's account of it: what observable, wrong output would that produce for <title>Test Page</title>, and why does the bug only show up on END tags, not start tags?

Reveal the answer

The text "Test Page" would end up appearing after EndTag("title") in the token list instead of between the start and end tags — and it would keep drifting further out of place, attaching itself to whatever the next flush happened to be (in the real run, it surfaced after EndTag("head") too, right before the next start tag). It only shows up on end tags because the original code's `_consume_markup` had an explicit `self._emit_text_if_any()` call in the start-tag branch, but the end-tag and comment branches jumped straight to consuming the tag/comment without that call — an easy one-line omission to make once, and easy to miss by reading the code, because the start-tag path (the one everybody tests first, since most HTML opens far more tags than it comments) looked completely correct. Running it against real markup with all three token types was what actually surfaced it.

There Are No Dumb Questions

Did the text-ordering bug in DECISIONS.md actually happen, or is it a made-up teaching example?
It actually happened, in this exact file, during this exact module's development — the first real run's output showed Text("Test Page") appearing after EndTag("head") instead of between <title> and </title>. That's precisely why this course's process insists on running every module and checking real output before writing documentation about it — the bug was invisible from reading the code alone.
Why does a comment's content just get grabbed with `str.find`, when tags get a whole careful state machine?
Because nothing inside a comment is ever re-interpreted as markup, no matter what it looks like — <!-- a comment with <fake> tags inside --> proves this: the fake tag never becomes a real `StartTag` token. Once you know "everything up to the next `-->` is opaque data," a direct search is both correct and simpler than modeling states for content that's never actually parsed further.
What happens to `&` in this tokenizer — does it become `&`?
No — it stays as the four literal characters `&`. Entity decoding is a real, separate piece of the HTML spec this module deliberately doesn't implement (DECISIONS.md). Every sample HTML this course uses from here forward is written to not depend on it.
