The Big Analogy

🍽️ The Restaurant, continued

The calculator (Module 18) is placed on the actual counter, and someone hands it a specific set of buttons wired to real kitchen actions: press this button and it looks up a specific plate by its ticket number; press that one and it actually changes what's written on that plate's label — for real, not on a copy. The calculator still doesn't "understand" the kitchen — it just has a fixed set of buttons that happen to be wired to real consequences now.

What Happens, Step by Step

  1. Before running any script, hold a real Python reference to a specific DOM element (proving, later, that we're looking at the SAME object the script touched — not a fresh copy).
  2. Register a handful of Python functions — getElementById, setText, setAttribute, etc. — into the interpreter's global scope, exactly the way Module 18 registered print.
  3. Run a script that calls these functions by name — from the interpreter's point of view, they're indistinguishable from any other function.
  4. getElementById returns the real Element object, not a copy — every subsequent binding call receives and mutates that same object.
  5. After the script finishes, read the ORIGINAL Python reference held in step 1 — if the mutations are real, they're visible there too, with zero re-fetching.

A Map of the Binding

Python: target = find_element_with_id("target") <- a real reference, held BEFORE any script runs JS: let el = getElementById("target"); \_____________________/ Python function, called like any JS function returns the SAME object `target` points to JS: setText(el, "Updated by JS!"); \___________________/ mutates el.children DIRECTLY — `el` IS `target` Python (AFTER the script, using the SAME `target` reference): target.children -> [Text('Updated by JS!')] ^^^^^^^^^^^^^^^^^^^^^^^ the mutation is visible here — proof it was a REAL mutation, not a copy

one object, two "sides" (Python and JS) touching it — that's the entire binding

The Code, Explained

Registering a binding looks EXACTLY like registering print did in Module 18 — because it's the same mechanism, unmodified:

dom_bindings.py
def js_setText(el: Element, text: str) -> None:
    el.children = [TextNode(text, parent=el)]

interp.global_env.declare("setText", js_setText)

Nothing in Module 18's `eval_Call` needed to change to support this — it already accepted any Python callable:

js_interpreter.py (Module 18, unmodified)
if callable(callee):
    return callee(*args)

Limits / What You Cannot Do Yet

Can't do yet

  • Property syntax (el.textContent = "...") — Module 18 has no . operator, so every binding is a plain function call
  • querySelector, removeChild, or event listeners — Module 20's job
  • Trigger any re-layout or re-paint after a mutation — the render pipeline doesn't know anything changed yet

Can do now

  • Look up a real DOM element by id from inside a running script
  • Read and mutate its text and attributes, with the mutation OBSERVABLE outside the script
  • Create new elements and actually append them into the real tree

⚠ Getting a blank or broken result?
  • The AFTER checks fail even though the script's own print() output looks right: this is the exact bug this module's design is meant to catch — check `getElementById` is returning the actual object (`return el`), not something derived from it (like a copy or a string summary).
  • LookupError: no element with id: confirm the id you're searching for actually exists in the parsed HTML, and that `_find_by_id` is searching `Element` children, not skipping past `TextNode` siblings incorrectly.

Brain Exercise

🧠 Think before you reveal

Suppose `js_getElementById` were written to return `Element(tag=el.tag, attrs=dict(el.attrs), children=list(el.children))` — a fresh COPY of the found element, instead of `el` itself. Which specific checks in this module's test would start failing, and which (if any) would keep passing?

Reveal the answer

The script's OWN print() output (checks against interp.output) would keep passing — the script would still see its own copy get updated correctly, because every binding call after `getElementById` would consistently operate on that same copy. But every check that inspects the ORIGINAL `target` reference held from before the script ran would fail: `target.attrs` would never gain `data-touched`, and `target.children` would never gain the new ``, because none of the script's mutations would ever reach the real object sitting in the real DOM tree — only its disconnected copy. This is exactly why this module verifies against the pre-held reference instead of only checking the script's own output: a copy-based bug would be invisible to the first kind of check and only shows up in the second.

There Are No Dumb Questions

Why does `setText` replace ALL children instead of trying to find and update just the existing text?
Because that's what real DOM's `textContent` setter actually does — it's not a targeted edit, it's a full replacement. Matching that real behavior (rather than inventing a "smarter" partial-update version) means this binding's semantics are a recognizable subset of a real API, not something novel a learner would have to unlearn later.
Is it a problem that these bindings are function calls instead of `el.property = value`?
It's a real, honest simplification, not a hidden one — DECISIONS.md names it directly as a consequence of Module 18 not parsing `.`. If Module 18 were extended with property-access syntax later, these exact same Python functions could be re-exposed as property getters/setters with no change to their own logic — only to how the interpreter calls them.
Why doesn't this module also make the page visually update when the script changes something?
Because nothing in this course's pipeline yet knows a mutation happened — Modules 10-16 (layout through compositing) only ever ran ONCE, on the original DOM, and have no mechanism to notice a change and redo their work. That noticing-and-redoing mechanism is specifically what Module 20 builds next.

What's Next

A script can now genuinely change the DOM — but the screen wouldn't reflect it, because nothing re-runs layout or paint afterward. Module 20 builds the invalidation pipeline: the mechanism that notices a mutation happened and correctly redoes only the affected parts of Modules 9 through 16's work.
