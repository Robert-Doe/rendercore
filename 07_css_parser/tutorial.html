CSS Tokenizer & Parser

CSS gets its own tokenizer and parser, completely independent of HTML's — because it's a completely independent grammar.

The Big Analogy

🍽️ The Restaurant, continued

This is the pastry chef reading the house style guide — a completely separate document from the order slip, written in its own format. Its entries look like "for any dish tagged 'soup', use the blue bowl" — a description of which dishes it applies to (the selector) and what to do for them (the declarations). The style guide doesn't know or care what order the actual dishes will come out in — it's read once into a reference list, consulted per-dish later. That "consulted later" step is Module 8; this module only builds the reference list.

What Happens, Step by Step

  1. Strip /* comments */ — they carry no meaning past this point.
  2. Repeatedly find the next {: everything before it (up to the last rule's }) is selector text.
  3. If that selector text starts with @ (an at-rule like @media), skip the entire block — including any braces nested inside it — unparsed.
  4. Otherwise, find the matching }, split the selector text on commas into one or more individual selectors, and parse the block between the braces as declarations.
  5. Each selector splits on whitespace into compound selectors (descendant combinators), and each compound splits into an optional type name plus any .class and #id pieces.
  6. Each declaration splits on : into property/value, with a trailing !important detected and stripped into its own flag.

A Map of a Parsed Rule

nav a.active { color: red; } \_____________/ \____________/ selector declarations "nav a.active" --> Selector([ SimpleSelector(type='nav'), SimpleSelector(type='a', classes=['active']), ]) \_____________/ \_______________________/ ancestor the element itself (descendant combinator = whitespace between them) "color: red;" --> [ Declaration(property='color', value='red', important=False) ]

a Selector is a left-to-right ancestor chain; a Rule pairs a list of these with a list of declarations

The Code, Explained

The at-rule skip is one `if`, but it's the difference between handling a real stylesheet and crashing on the first `@media` block:

css_parser.py
if header.startswith("@"):
    i = _skip_block(css, brace_idx)   # depth-aware: handles nested { }
    continue

_skip_block counts brace depth rather than just finding the next }, because an @media block's closing brace isn't the first one encountered — there's a whole nested rule (body { font-size: 14px; }) inside it first.

The compound-selector parser is a small loop that never needs to know in advance how many classes a selector has:

css_parser.py
while i < n:
    marker = token[i]      # '.' or '#'
    i += 1
    start = i
    while i < n and token[i] not in ".#":
        i += 1
    piece = token[start:i]
    if marker == ".":
        classes.append(piece)
    elif marker == "#":
        id_ = piece

This is what lets div.card.featured#hero — three qualifiers on one element — parse correctly without any special-casing for "how many classes."

Limits / What You Cannot Do Yet

Can't do yet

  • Parse child (>), sibling (+, ~) combinators — descendant only
  • Evaluate @media conditions — they're skipped, not applied
  • Decide which rule wins a conflict (that's specificity — Module 9)
  • Handle attribute selectors ([type="text"]) or pseudo-classes (:hover)

Can do now

  • Parse type, class, id, universal, and compound selectors
  • Parse comma-separated selector groups sharing one declaration block
  • Parse descendant-combinator selectors like nav a.active
  • Correctly detect !important and skip unsupported at-rule blocks without crashing

⚠ Getting a blank or broken result?
  • Rule count includes the @media block's inner rule: check _skip_block is tracking brace depth, not just finding the first } after the at-rule starts.
  • !important not detected: confirm there's no space between the value and !important in your test input — this module's detection is deliberately narrow (DECISIONS.md).

Brain Exercise

🧠 Think before you reveal

Given that this parser only understands the descendant combinator, what would _parse_compound() actually produce for the token > if someone wrote nav > a.active as a selector — and would it fail loudly or silently?

Reveal the answer

Silently — no exception. text.split() on "nav > a.active" produces three tokens: "nav", ">", and "a.active". The middle token ">" gets fed into _parse_compound(), whose first character isn't . or #, so the whole string ">" is read as a type name — producing a nonsensical SimpleSelector(type_name='>') that will never match any real element, silently making the whole selector match nothing. This is exactly the kind of gap DECISIONS.md names explicitly rather than letting a learner discover it by surprise: unsupported syntax here doesn't crash, it just quietly fails to match anything, which is arguably worse to debug than a loud error.

There Are No Dumb Questions

Why does the demo output print .card back as *.card?
SimpleSelector.__repr__ always shows a type position, defaulting to * when `type_name` is `None` — purely a printing choice to make "no type constraint" visible, not a sign the parser rewrote your selector. Internally, `.card` and `*.card` are stored identically, because they mean the same thing.
Why does this module bother skipping `@media` blocks instead of just refusing to handle them (crashing loudly)?
Because real, ordinary stylesheets contain `@media` blocks constantly (responsive design depends on them), and a browser that crashed on the first one would be unable to render a huge fraction of real pages — the same reasoning Module 6 used for silently ignoring stray end tags. "Unsupported" and "fatal" are different categories; skip-and-continue keeps everything else in the stylesheet usable.
Couldn't the declaration parser get confused by a value that itself contains a colon, like a URL?
Potentially, yes — `partition(":")` splits on the FIRST colon only, so `background: url(http://example.com/a.png)` would correctly keep `url(http://example.com/a.png)` as one value (since only the first colon after "background" is used as the split point). But a value containing a semicolon inside quotes would break the declaration-splitting logic, since `text.split(";")` has no awareness of string quoting. This module doesn't defend against that — a real limitation worth knowing, not silently glossed over.
