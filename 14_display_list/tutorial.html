The Big Analogy

🍽️ The Restaurant, continued

Every dish is plated, every garnish is decided, every plate's position on the table is finalized. Now someone has to write the expo's plating checklist — a single, ordered list: "set the tablecloth, then the base plate for table 3, then table 3's sauce, then table 3's garnish, then move to table 5's base plate..." The person carrying out that checklist (Module 15) doesn't need to know anything about recipes or seating charts anymore — just: read the next line, do exactly that, move on. This module writes the checklist. It doesn't do any of the plating itself.

What Happens, Step by Step

  1. For the current box: if it has a background color, emit one DrawRect command for its area.
  2. If it has a visible border, emit one DrawBorder command — AFTER the background, so the border visually sits on top of the fill.
  3. Sort this box's children into paint order using Module 13's paint_order() — reused directly, not reimplemented.
  4. For each child, in that order, recursively repeat this whole process and append its commands to the running list.
  5. Return one flat list — no nesting, no tree structure left in it at all.

A Map of the Flattening

TREE (paint order already applied to children: B, A, C): root (gray) ├── B (z=-1, blue) ├── A (z=0, red) └── C (z=0, green) └── D (border only, purple) FLATTENED DISPLAY LIST: [0] DrawRect root gray <- parent's own command, always first [1] DrawRect B blue <- z=-1: painted before its z=0 siblings [2] DrawRect A red <- z=0, 1st in DOM among the z=0 group [3] DrawRect C green <- z=0, 2nd in DOM among the z=0 group [4] DrawBorder D purple <- C's CHILD: only after C's own command

the tree shape is gone by the end — only the sequence survives, and the sequence IS the correctness guarantee

The Code, Explained

The reuse of Module 13 is the line worth lingering on — not because it's complex, but because it's a real design choice about NOT duplicating logic:

display_list.py
from flex_and_stacking import StackItem, paint_order   # Module 13, unmodified

stack_items = [StackItem(label=c.label, z_index=c.z_index, tree_order=i)
               for i, c in enumerate(box.children)]
ordered = paint_order(stack_items)

And the order that makes the whole thing correct — self, then children, always in that order:

display_list.py
if box.background:
    items.append(DrawRect(...))          # 1. this box's own fill
if box.border_color and box.border_width > 0:
    items.append(DrawBorder(...))         # 2. this box's own border
for stacked in ordered:
    items.extend(build_display_list(child))   # 3. THEN children, recursively

Limits / What You Cannot Do Yet

  • Actually draw anything — these are still just data structures, no pixels exist yet
  • Text commands aren't wired in from Module 12 yet (structurally trivial, just not connected in this module's demo)
  • Real nested stacking contexts (inherits this gap directly from Module 13)

Can do now

  • Flatten an arbitrarily nested tree into one correctly-ordered list
  • Correctly respect z-index reordering when flattening, not just DOM order
  • Correctly keep a box's own paint commands ahead of its children's

Checks
======================================================================
root's own background is drawn FIRST, before any child: True
B (z=-1) painted before A and C (z=0) despite being 2nd in DOM: True
A painted before C — both z=0, DOM order (A then C) breaks the tie: True
D's border command appears AFTER C's own background (children paint after their own parent's commands): True

⚠ Getting a blank or broken result?
  • A parent's background ends up AFTER its children in the list: check the background/border appends happen before the children loop, not after — this is the single most consequential ordering bug this module can have.
  • z-index seems ignored, children paint in plain DOM order: check `paint_order()` is actually being called on the children, and its RESULT (not the original `box.children` list) is what's iterated.

Brain Exercise

🧠 Think before you reveal

Suppose, instead of appending a box's own commands before recursing into children, the code appended them AFTER. For the sample tree in this module, name one SPECIFIC visual bug this would cause once Module 15 actually draws it.

Reveal the answer

The root's gray 200×200 background would be drawn LAST, on top of every other rectangle already drawn — completely covering B, A, C, and D's border, since a later draw command paints over an earlier one at the same location. The page would render as one solid gray rectangle with nothing visible inside it, despite the display list containing all the correct commands with all the correct colors and positions — the DATA would be entirely correct, and the render would still be completely wrong, purely from ordering. This is exactly why Module 14's "what we proved" doesn't stop at "the right commands exist" — it specifically checks the ORDER they exist in.

There Are No Dumb Questions

Why is reusing Module 13's `paint_order()` presented as a notable decision instead of just... obviously the right thing to do?
Because "obviously right" and "actually done" aren't the same thing in real codebases — it would have been just as easy, and arguably faster in the moment, to write a second sort inline here. The DECISIONS.md entry exists to make the cost of NOT reusing it explicit: two copies of the same logic that can silently diverge the next time either one gets modified.
Is a display list basically the same idea as a call stack or an execution trace?
There's a real family resemblance — both are a linear sequence recording something that was structurally nested. But a display list is DATA, inspectable and replayable as many times as needed (Module 15 will replay it once; a real browser might replay a cached one many times without recomputing layout), where a call stack is a runtime mechanism, not a persisted artifact you hand to something else.
Why does `DrawBorder` need its own command type instead of just being another `DrawRect`?
Because they mean different things to whatever executes them: a filled rectangle versus an unfilled, stroked outline. Module 15's rasterizer will call a different Tkinter drawing method for each — collapsing them into one command type would just push the "which kind of drawing is this" decision to a later, less structured place.
