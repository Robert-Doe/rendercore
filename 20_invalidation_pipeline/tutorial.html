Invalidation & Re-render Pipeline

A page with a thousand elements changes one word. Redoing all thousand would be correct — and unacceptably wasteful.

The Big Analogy

🍽️ The Restaurant, continued

One dish on one table gets a bigger portion added mid-service. The head chef doesn't re-plate the entire dining room — they check: does this table's own tray have a FIXED size regardless of what's on it (say, a rigid serving board), or does the tray itself grow to fit its contents? If the tray is fixed-size, the chef knows the growth stops right there — nothing about any OTHER table needs to be touched at all, because nothing about them could possibly have changed. If the tray itself would need to grow, the chef has to check the NEXT container out, and the next, until they find one that's fixed. That boundary — the first fixed container, checked outward from the change — is exactly what this module computes.

What Happens, Step by Step

  1. A script (Module 19) mutates something about one DOM node's computed style — here, its height.
  2. Walk UP from that node's PARENT (never the node itself — see section 07) looking for the nearest ancestor with an EXPLICIT height.
  3. That ancestor is the relayout boundary: its own size is guaranteed unaffected by anything inside it, so it's safe to stop propagating the search there.
  4. Re-run Module 11's ordinary layout_block — unmodified — starting FROM that boundary, using its already-known containing block.
  5. Splice the resulting new subtree back into the existing layout tree at the correct position. Everything else in the tree is left completely, literally untouched.
  6. Regenerate a display list for just that subtree (Module 14, unmodified) — ready to be spliced into the canvas.

A Map of the Boundary Search

body (auto height) ├── #sidebar (auto height) <- UNTOUCHED branch │ └── #sidebar_item (height:80px) └── #main (height: 300px EXPLICIT) <- BOUNDARY: found here └── #target (height: 50px -> 150px, MUTATED) search starts at #target.parent = #main #main has EXPLICIT height -> STOP, this is the boundary re-layout runs ONLY on: #main, #target never touched: body, #sidebar, #sidebar_item PROOF: sidebar_layout_after IS sidebar_layout_before (same object!)

the search stops at the FIRST ancestor whose own size can't be affected — not at the DOM root

The Code, Explained

The boundary search, and the identity check that proves it worked:

invalidation.py
current = node.parent      # NEVER start at `node` itself — see section 07
while current is not None:
    style = styles.get(id(current), {})
    if style.get("height", "auto") != "auto":
        return current      # found a safe stopping point
    current = current.parent

Limits / What You Cannot Do Yet

Can't do yet

  • Splice specific real canvas items in/out of a live Tkinter canvas — demonstrated at the display-list level only
  • Handle mutations that themselves change WHICH properties are inherited (Module 9's cascade isn't re-triggered here — only layout is)
  • Batch multiple mutations in the same tick into one combined re-layout

Can do now

  • Correctly identify the smallest safe subtree to re-layout after a mutation
  • Prove — by object identity, not just matching output — that unaffected subtrees are never recomputed
  • Regenerate a correct, smaller display list for just the changed subtree

⚠ Getting a blank or broken result?
  • Boundary search returns the mutated node itself: this exact bug happened during development — check the search starts at node.parent, not node.
  • Identity checks fail (objects don't match): confirm the splice step only replaces the boundary's entry in its parent's `.children` list — accidentally rebuilding the WHOLE tree and comparing against a fresh copy would break every identity check, even for genuinely-unaffected nodes.

Brain Exercise

🧠 Think before you reveal

This module's own first version searched for a boundary starting AT the mutated node, not its parent — and returned the mutated node itself as "the boundary" every time. Walk through exactly what `layout_block(target_node, ...)` alone — with no connection to `#main` at all — would and wouldn't correctly compute, and why that's not sufficient.

Reveal the answer

Laying out `#target` in isolation WOULD correctly compute its own new content height (150px) — that part works fine on its own. But it has no way to know `#main`'s content width to use as a containing block (it would need that passed in from somewhere), and critically, re-laying-out `#target` alone does nothing to update `#main`'s awareness that its child grew — if `#main` had auto height instead of explicit, `#main`'s OWN height would need to change too, and nothing about re-laying-out `#target` alone would ever discover or apply that. The whole reason the search needs to go to the PARENT and check ITS height is to answer a question `#target` itself cannot answer about itself: "does my growth ripple outward, and if so, how far?" A node genuinely cannot determine its own blast radius — only something walking outward from it can.

There Are No Dumb Questions

What happens if NO ancestor has an explicit height — does the algorithm break?
No — `find_relayout_boundary`'s loop falls through to `last_seen`, the topmost ancestor reached, which correctly (if conservatively) means "re-layout the whole page." This is exactly the safe, correct fallback: worse-case performance, never worse-case CORRECTNESS. A real browser's actual relayout-boundary logic has more nuance (certain CSS properties like `contain` or `overflow` can also create boundaries), but "explicit height" alone is a real, valid instance of the same underlying idea.
Why does this module check `#main`'s height stayed exactly 300, instead of just checking `#target`'s new height?
Because checking only `#target`'s new value would prove the mutation "worked," but not prove the BOUNDARY CHOICE was safe. Confirming `#main`'s own height is unchanged is the concrete, checkable version of the abstract claim "an explicit height means this ancestor can't be affected by its children" — turning a design assumption into a verified fact about this specific run.
Is checking object identity (`is`) overkill compared to just checking the values look right?
For THIS module's specific claim — "was this subtree recomputed at all" — value-equality checks are actually insufficient, not just less elegant. A completely rebuilt-from-scratch `#sidebar` that happens to produce identical numbers would pass a value check while still representing exactly the wasted work this module exists to avoid. Identity is the only check that distinguishes "correctly reused" from "recomputed to the same answer."
