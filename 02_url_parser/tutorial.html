The Big Analogy

🍽️ The Restaurant, continued

Before the runner (Module 1) can be sent anywhere, someone at the host stand has to read the customer's request and split it into pieces: which warehouse to visit (the host), which loading dock number at that warehouse (the port), which specific crate to ask for (the path), any filtering instructions to hand the warehouse staff (the query — "only the ripe ones"), and a private note that only matters once the crate is already back on the table and is never spoken to the warehouse at all (the fragment — "open it at the garnish, not the entrée").

Get any of the first four wrong and the runner goes to the wrong place, or asks for the wrong thing. Get the fragment wrong and nothing about the trip changes at all — it only affects what happens after the crate is already home.

What Happens, Step by Step

  1. Strip off the fragment first (everything after the first #) — it can contain characters (?, /) that would otherwise be misread as part of the query or path.
  2. Find "://" to split off the scheme and confirm it's one this course supports (http or https).
  3. Take everything up to the next / or ? as the authority, and split it on the last : into host and port (if a port is present).
  4. If no port was given, default it from the scheme — 80 for http, 443 for https.
  5. Split whatever's left on ? into path and query.
  6. If the path came out empty, default it to "/" — HTTP defines a missing path as a request for the root.

A Map of a URL

https://example.com:8080/search?q=browsers&page=2#results \___/ \_________/ \__/ \_____/ \________________/ \_____/ scheme host port path query fragment \_____________________/ authority parse order: 1) strip fragment 2) split scheme 3) split authority 4) split host:port 5) split path/query 6) default path "/"

left-to-right parsing order matches the grammar's own left-to-right structure

The Code, Explained

The most important line in the whole module is the first real one — because getting the order wrong here breaks everything downstream:

url_parser.py
if "#" in rest:
    rest, fragment = rest.split("#", 1)
else:
    fragment = ""

This runs before scheme, authority, or query are touched. A fragment like #a?b contains a literal ? — if we split on ? first, that character would get misread as the start of a query string that was never there. Stripping the fragment first removes that ambiguity structurally, rather than trying to detect it with a smarter regex later.

The host/port split reuses a small but deliberate detail — rsplit, not split:

url_parser.py
if ":" in authority:
    host, port_str = authority.rsplit(":", 1)

rsplit(":", 1) splits from the right, at most once — so it correctly separates example.com:8080 into example.com and 8080. (This module doesn't support IPv6 literal hosts like [::1]:8080, which contain extra colons — see DECISIONS.md for why that's explicitly out of scope.)

Limits / What You Cannot Do Yet

Can't do yet

  • Parse IPv6 literal hosts ([::1])
  • Parse userinfo (user:pass@host)
  • Resolve relative URLs with .. segments
  • Handle schemes other than http/https

Can do now

  • Parse any http/https URL into scheme/host/port/path/query/fragment
  • Correctly default missing ports and missing paths
  • Resolve a simple absolute-path relative reference against a base URL
  • Prove correctness against Python's own urllib.parse, used only as a test oracle

⚠ Getting a blank or broken result?
  • ValueError: unsupported scheme: you passed something other than http/https (e.g. ftp://) — this is a deliberate scope limit, not a bug (DECISIONS.md).
  • ValueError: relative URL given with no base: a string with no "://" was parsed without a base= argument — pass the current page's URL as the base, the way a real browser resolves a link relative to the page it's on.
  • MISMATCH in the urllib cross-check: if you edit the parser and see this, trust `urllib` here — it's the reference implementation for this comparison.

Brain Exercise

🧠 Think before you reveal

Consider the URL https://example.com/faq#what-is-a-query?. That fragment contains a literal ? character. Does this parser incorrectly split off a query string from it? Why or why not?

Reveal the answer

No — and the reason is entirely step 1. parse_url() splits on the first # before it ever looks for a ?. By the time the query-splitting code runs, the string being examined is just https://example.com/faq — the fragment (what-is-a-query?, ? and all) has already been captured whole and set aside. If the code instead searched for ? first, across the entire original string, it would incorrectly treat everything after that ? as a query string and mistakenly shrink the fragment down to nothing. This is exactly why DECISIONS.md calls the fragment-first ordering "forced by the grammar," not a style choice — reordering these two steps produces observably wrong output on inputs exactly like this one.

There Are No Dumb Questions

Why does URL have an origin() method at all — isn't that just scheme + host + port pasted together?
Mechanically, yes — but giving it a name matters. Module 23 (same-origin policy) will compare two URLs' origins constantly, and writing url_a.origin() == url_b.origin() makes the security-relevant comparison explicit in the code, instead of it being an easy-to-miss three-field comparison scattered everywhere it's needed.
Why bother cross-checking against urllib.parse if the whole point is not using it?
Those are two different things: not using urllib.parse to do the parsing (the deliverable stays from-scratch) versus using it to check our work after the fact. It never appears above the if __name__ == "__main__": line — see DECISIONS.md's last entry for exactly where the line is drawn.
What happens if I pass a URL like "about.html" with no base?
It raises ValueError immediately, rather than guessing. A relative reference is only meaningful in the context of "relative to what page," so this parser refuses to silently invent one. Later, when Module 6+ builds pages containing relative links, the current page's own URL is what gets passed as base.
Why is an empty path turned into "/" instead of being left empty?
Because Module 3 puts this exact string into the request line it sends to the server (e.g. GET / HTTP/1.1), and an empty request path isn't valid there — HTTP requires at least /. Defaulting it here means every later module can assume path is never an empty string.
