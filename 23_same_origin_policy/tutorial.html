Same-Origin Policy

Every module before this one trusted the script it was running. This one is where trust becomes conditional.

The Big Analogy

🍽️ The Restaurant, continued

Every table gets its own private bill, and staff won't hand table 9's bill to someone sitting at table 5 — even if that person insists they're "basically the same restaurant." But if TWO different guests are both seated at tables that belong to the SAME account (say, a company that booked two tables under one name), staff will treat requests from either table as coming from that shared account. The rule was never "no one can ever see another table's bill" — it's "the account has to actually match," checked every single time, not assumed.

What Happens, Step by Step

  1. Every tab is registered with its real origin — computed from its URL (Module 2), not asserted by the tab itself.
  2. When a script asks to read another tab's document or cookies, the request carries the ASKING tab's origin, fixed when its interpreter was created — never something the script can change mid-run.
  3. The registry — a component outside any individual tab — compares the asking origin against the target tab's real origin.
  4. Exact match → real access is granted, and the requesting script gets real data back.
  5. Any mismatch — different host, different scheme, or different port — → a SecurityError is raised, denying the access outright.

A Map of the Four Tabs

tab "bank" -> https://bank.example.com:443 (the target, real data) tab "evil" -> https://evil.example.com:443 (different HOST) tab "bank2" -> https://bank.example.com:443 (SAME origin as bank) tab "bank_http" -> http://bank.example.com:80 (same HOST, different SCHEME) evil -> access bank's document -> DENIED (host differs) bank2 -> access bank's document -> ALLOWED (exact origin match) evil -> access bank's cookies -> DENIED (host differs) bank_http -> access bank's document -> DENIED (scheme differs, host does NOT save it)

the check is scheme AND host AND port, together — matching any two isn't enough

The Code, Explained

The entire enforcement is one comparison, in one place outside any tab's own script:

same_origin.py
def access_document(self, requesting_origin, target_tab_id):
    target = self.tabs[target_tab_id]
    if requesting_origin != target.origin:
        raise SecurityError(...)
    return target.document

And the origin a script is allowed to claim is fixed the moment its interpreter exists — never something the running script itself controls:

same_origin.py
def make_interpreter_for(registry, own_origin):
    def js_accessForeignDocument(target_tab_id):
        return registry.access_document(own_origin, target_tab_id)   # own_origin: closed over, fixed
    ...

Limits / What You Cannot Do Yet

Can't do yet

  • Any of the real, deliberate escape hatches (CORS headers, postMessage) that let origins opt INTO limited cross-origin communication
  • Enforce this at the process level — see Module 24 for the OS-backed version of this same boundary
  • Recover from a denial inside the script itself — Module 18 has no try/catch

Can do now

  • Provably deny cross-origin document and cookie access
  • Provably ALLOW same-origin access — a real, working ALLOW path, not just an absent DENY
  • Correctly distinguish "same host, different scheme" from genuinely same-origin

Brain Exercise

🧠 Think before you reveal

Suppose `make_interpreter_for` were changed so a script could call a new function, `setMyOrigin(fake_origin)`, that reassigned `own_origin` to whatever string the script wanted, before calling `accessForeignDocument`. What would this completely undermine, and why would it be worse than simply not having a same-origin policy at all?

Reveal the answer

It would undermine the ENTIRE policy, completely — any script could simply call setMyOrigin("https://bank.example.com:443") right before requesting access to the bank tab, and the check would pass every time, for every tab, regardless of where the script actually came from. This is arguably worse than having no policy at all, because a missing policy is at least honestly absent — a policy that LOOKS like it enforces a boundary but can be trivially bypassed by the exact party it's supposed to restrict creates false confidence. This is precisely why `own_origin` is captured once, at interpreter-creation time, by code OUTSIDE the script's own control, with no binding ever exposed that lets a running script rewrite it — the trustworthiness of a security check depends entirely on what the party being checked can and can't influence.

There Are No Dumb Questions

Is `BrowserRegistry` a realistic model of how real browsers enforce this, or a simplification?
It's a real, structurally accurate simplification — real browsers enforce same-origin checks in a privileged part of the browser (historically the browser process, or specific trusted code within the renderer that the untrusted page script can't reach), never inside code the page's own script could tamper with. `BrowserRegistry` living outside any tab's interpreter is a small-scale version of exactly that separation.
Why does TEST 4 matter as much as TEST 1 — isn't "different hostname" the obvious case?
Because "same hostname, different scheme" is the subtler, more realistic way a same-origin check actually gets implemented WRONG — a hostname-only comparison looks correct in the common case (most cross-origin attacks do involve a different hostname) and only reveals its flaw against exactly this kind of same-host, different-scheme scenario, which is precisely why it's tested explicitly here rather than assumed to follow automatically from TEST 1 passing.
What would a real browser do differently if TEST 1's denied access were attempted from actual JavaScript?
A real browser would typically throw a catchable `DOMException` (often "SecurityError" or a same-origin-related message) that the page's own `try`/`catch` COULD handle gracefully. This module's denial is an uncaught Python exception that halts the script entirely, because Module 18 doesn't implement `try`/`catch` — a real, named simplification, not a claim this matches real JS error-handling exactly.

What's Next

This module's boundary is entirely logical — enforced by code choosing not to return data. Module 24 adds the OS-backed version of the same idea: running each tab in a genuinely separate operating system process, so a crash or a memory-corruption bug in one tab's renderer can't even theoretically reach another tab's memory, regardless of what any in-process check does or doesn't allow.
