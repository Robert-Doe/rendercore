The Big Analogy

🍽️ The Restaurant, continued

This module builds a calculator that can also follow multi-step instructions and remember things — genuinely useful on its own, sitting on a counter, with no idea a restaurant exists around it. It doesn't know about tables, orders, or plates. What makes it USEFUL to the restaurant is entirely a later decision: someone chooses to hand it specific numbers from specific orders and read specific results back. Building the calculator and wiring it into restaurant operations are two different jobs — this module is only the first one.

What Happens, Step by Step

  1. Tokenize: turn source text into numbers, strings, identifiers, keywords, and operators — the same state-machine-style scanning idea as Module 5, applied to a different grammar.
  2. Parse: build a tree (an AST) via recursive descent, one method per precedence level, so 2 + 3 * 4 naturally groups as 2 + (3 * 4).
  3. Evaluate statements by walking the tree: a VarDecl declares a variable in the current scope; an If evaluates its condition and executes one branch; a For runs its init once, then loops while its condition holds.
  4. Evaluate expressions recursively: a BinOp evaluates both sides, then applies the operator; a Call evaluates the callee and arguments, then runs the function's body in a NEW scope.
  5. That new scope's PARENT is the function's closure environment — the scope it was originally defined in, not the scope it's being called from. This one detail is the entire reason closures work correctly.

A Map of a Closure

function makeCounter() { let n = 0; function increment() { n = n + 1; return n; } return increment; } let counter1 = makeCounter(); // call #1 to makeCounter let counter2 = makeCounter(); // call #2 to makeCounter — a SEPARATE call makeCounter call #1 creates env_A { n: 0 } increment's closure_env = env_A returns the increment FUNCTION VALUE (with env_A attached) counter1 = that function, remembering env_A forever makeCounter call #2 creates env_B { n: 0 } <- a DIFFERENT n! counter2 = increment remembering env_B counter1(); -> call_env's parent = env_A -> env_A.n becomes 1 counter1(); -> env_A.n becomes 2 counter1(); -> env_A.n becomes 3 -> returns 3 counter2(); -> call_env's parent = env_B -> env_B.n becomes 1 -> returns 1 (env_B was NEVER touched by counter1 at all)

two calls to the SAME function created two SEPARATE environments — that separation is what closures actually are

The Code, Explained

The single line that makes closures work — get this wrong and every closure in every JS program ever run through this interpreter breaks:

js_interpreter.py
def eval_Call(self, e, env):
    callee = self.eval_expr(e.callee, env)
    args = [self.eval_expr(a, env) for a in e.args]
    if isinstance(callee, Function):
        call_env = Environment(callee.closure_env)   # <- NOT `env` (the caller's scope)
        for param, arg in zip(callee.params, args):
            call_env.declare(param, arg)

callee.closure_env was captured back when the function was DEFINED (in exec_FunctionDecl, env at that moment becomes closure_env). Using the CALLING code's env instead here — an easy mistake to make, since env is right there and looks like the obvious choice — would implement "dynamic scoping" instead of the lexical scoping real JavaScript actually has, and this module's two-independent-counters test would fail immediately.

Recursion works with zero special-casing, because a function calling itself is just... a function call, evaluated the same way as any other:

js_interpreter.py
return n * factorial(n - 1);
# factorial is just an Ident lookup -> a Function value -> eval_Call runs it,
# same code path as calling any other function

Limits / What You Cannot Do Yet

Can't do yet

  • Objects, arrays, or ./[] property access
  • ++/-- — write i = i + 1 instead
  • JS-style loose == type coercion — this interpreter's == behaves like real JS's ===
  • Anything resembling the DOM — this interpreter has never heard of an element

Can do now

  • Run real recursive functions correctly
  • Run real, independent closures correctly — the hardest thing to get right in this module
  • Correct operator precedence for arithmetic, comparison, and logical expressions
  • Correct scoping for let/var, blocks, loops, and function parameters

⚠ Getting a blank or broken result?
  • Both counters share state (counter2 shows 4, not 1): check `call_env`'s parent is `callee.closure_env`, not the caller's `env` — this is THE bug this whole module is designed to make visible.
  • NameError on a variable that should exist: check the relevant scope actually called `declare()` — a common mistake is calling `set_existing()` (which requires the variable to already exist somewhere) where `declare()` (which creates it) was needed.
  • SyntaxError: unexpected token: the tokenizer doesn't support every JS syntax form — check DECISIONS.md's scope-out list before assuming it's a bug.

Brain Exercise

🧠 Think before you reveal

If eval_Call used Environment(env) (the CALLER's scope) instead of Environment(callee.closure_env), would factorial's recursion still work correctly? Would the two-counters test still pass? Are these the same question?

Reveal the answer

They're NOT the same question, and that's the interesting part. factorial would still work fine even with the "wrong" (caller's-env) version — because every call to `factorial` happens from inside code that already has `factorial` itself in scope (it's a global function, visible everywhere), so which environment gets used as the parent doesn't actually change what's visible to the function body in this particular case. The two-counters test would break immediately, though: `increment`'s whole purpose is to see the SPECIFIC `n` that existed at ITS OWN definition site inside one particular call to `makeCounter` — using the caller's environment instead would have `counter1()` and `counter2()` both look up `n` wherever they happen to be CALLED from (both from the global scope, in this test), finding no `n` there at all, or the wrong one if one happened to exist. This is exactly why a bug like this can hide for a long time in real code: many ordinary function calls don't exercise the distinction between lexical and dynamic scoping at all — only closures, which capture and depend on a SPECIFIC enclosing scope, expose it.

There Are No Dumb Questions

Why does this interpreter's `==` behave differently from real JavaScript's?
Real JS's `==` performs a genuinely complex set of implicit type conversions before comparing — famous, widely-mocked examples include `[] == false` being `true`. Implementing that table correctly would be real, non-trivial work for a comparison operator most style guides tell working JS developers to avoid using anyway (in favor of `===`). This interpreter's `==` simply behaves like `===` always — a named, deliberate simplification, not an attempt at spec accuracy.
Why implement `return` using a Python exception instead of some other mechanism?
Because `return` needs to unwind out of however many nested blocks it's inside — potentially several `if`/`while`/`for` bodies deep — immediately, back to the function call site. Python's own exception propagation already does exactly this kind of "unwind through arbitrarily nested calls until something catches it" behavior, so reusing it avoids threading a manual "has this function returned yet?" signal through every single statement-execution method.
Could this interpreter be extended to support objects and arrays later?
Yes, and the shape of the extension is fairly predictable: a new AST node for object/array literals, a new AST node for `.`/`[]` access (parsed at the same precedence level as function calls in `parse_call`), and a Python dict or list as the runtime representation. It's real work, not a small tweak — which is exactly why DECISIONS.md names it as the largest scope-out in this module rather than something trivially bolted on.
