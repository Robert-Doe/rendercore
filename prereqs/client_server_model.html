The Client–Server Model

One side always speaks first, the other side always waits to be spoken to — and neither side can safely assume anything the other side didn't explicitly say.

🍽️ The Restaurant

The customer (client) never walks into the kitchen and starts cooking. They speak one order to the runner and then wait. The kitchen (server) never sends food to a table that didn't order — it only ever responds to a request it received. The whole relationship is asymmetric on purpose.

The Core Idea

A browser is a client. It always initiates: it opens the connection, sends the request, and then waits. A web server is oblivious to your browser's existence until a request arrives on a port it's listening on. This isn't a technical accident — it's the entire shape of the protocol: one request, one response, connection can close. Every module that talks over the network in this course (1, 3, 4) is implementing exactly one side of that shape: the client side.

Critically: a response is not guaranteed to arrive, arrive complete, or arrive quickly. A well-built client never assumes the server behaved — it reads exactly what came back, checks it, and handles the case where it didn't.

A Worked Example

Every HTTP exchange in this course has the same two-message shape:

CLIENT -> SERVER
GET /index.html HTTP/1.1
Host: example.com

SERVER -> CLIENT
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 137

<html>...</html>

Notice the client's message ends with a blank line and stops — it does not keep talking. The server reads that as "the request is complete," does its work, and sends back exactly one response. Module 3 builds both directions of this by hand.

Where This Shows Up In The Course

  • Module 1 — opens the connection the client side initiates.
  • Module 3 — formats the request (client → server) and parses the response (server → client), never the reverse.
  • Module 4 — proves the same request/response shape works unmodified once wrapped in TLS.
  • Module 21 — the chrome UI is what decides when to start a new request/response cycle (typing a URL, clicking a link, pressing back).
🧠 Quick check
Why can't a server just "push" a page update to your browser whenever it wants, in this model?

Because the server never initiates — it can only respond to a request it already received. This is precisely why real-time features (chat, live scores) need extra mechanisms layered on top (long-polling, WebSockets, Server-Sent Events) that this course doesn't build — they exist specifically to work around the one-request-one-response limit of the base model.
