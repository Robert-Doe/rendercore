Event-Driven Programming

A browser doesn't run top-to-bottom and stop. It sits idle, waiting for something to happen, then runs a small piece of code in response — forever.

🍽️ The Restaurant

The head waiter doesn't stand at table 5 executing a fixed script from a card. They wait, doing nothing, until something happens — a hand raised, a call of "check please" — and only then do they run the one specific response that event calls for. Between events, they're not "paused" in the middle of some other task; they're simply waiting for the next one.

The Core Idea

In event-driven programming, you don't write "the" program as one top-to-bottom sequence. Instead, you register small functions — handlers — each tied to a specific kind of event ("when a click happens, run this"). The program then sits in a loop, waiting for events, and whenever one occurs, it runs the matching handler to completion, then goes back to waiting.

The critical guarantee this depends on: one handler always runs to completion before the next one starts. Nothing interrupts a handler partway through. This is what makes it safe for a handler to freely read and modify shared state (like the DOM) without worrying that another handler is doing the same thing at the exact same instant.

A Worked Example

handlers = {"click": on_click, "keydown": on_keydown}

while True:                      # the event loop
    event = wait_for_next_event()      # blocks until something happens
    handler = handlers[event.type]
    handler(event)                     # runs fully before the loop continues

Nothing else runs while handler(event) is executing — not another handler, not a re-render. That's not a limitation; it's the whole point. Module 17 builds exactly this loop; Module 20 is what makes sure a handler that mutates the DOM leaves the render pipeline in a state it can correctly resume from once the handler returns.

Where This Shows Up In The Course

  • Module 17 — builds the loop itself: wait, dispatch, run to completion, repeat.
  • Module 19 — script registers handlers (e.g. onclick) through the DOM bindings; those handlers are what the loop calls.
  • Module 20 — a handler that mutates the DOM mid-run is exactly the trigger the invalidation pipeline watches for.
🧠 Quick check
If a click handler runs an infinite loop by accident, what happens to the rest of the page?

Everything freezes — no other events get processed, no re-render happens, the whole tab appears hung — because the loop is waiting for that one handler to return, and it never will. This is the real, exact cause of the "page unresponsive" behavior you've seen in a real browser, and it's a direct, unavoidable consequence of the "one handler runs to completion" guarantee explained above: the same rule that makes DOM mutations safe is what makes a runaway handler catastrophic.
