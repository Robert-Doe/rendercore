State Machines

A tokenizer doesn't "understand" text. It's a very small number of moods, and a strict rule for which mood comes next given the next character.

🍽️ The Restaurant

A waiter taking a spoken order is always in exactly one "mode": either listening for a dish name, or — the moment they hear the word "no" — listening for what to remove. Hearing "onions" means something completely different depending on which mode the waiter is currently in. The waiter never needs to remember the whole conversation — just which mode they're in right now, and what the next word does to that mode.

The Core Idea

A state machine is a system that is always in exactly one named state out of a small, fixed set, and has explicit rules for which state comes next given the current state and the next input. Crucially, it has no memory beyond "which state am I in" — it doesn't need to remember everything it's already seen.

This is exactly how a real tokenizer works. An HTML tokenizer reading character by character is, at any instant, in a state like TEXT, TAG_OPEN, or ATTRIBUTE_NAME. Seeing the character < while in TEXT means "finish the text token, switch to TAG_OPEN." Seeing that same character while already inside a tag means something else entirely. The state is what gives the same character a different meaning depending on context.

A Worked Example

A tiny state machine for recognizing the text <p>:

STATE: TEXT
  see '<'      -> emit any buffered text, go to STATE: TAG_OPEN
  see anything  -> buffer the character, stay in STATE: TEXT

STATE: TAG_OPEN
  see a letter  -> start buffering a tag name, go to STATE: TAG_NAME
  see '/'       -> this is a closing tag, go to STATE: TAG_NAME (closing)

STATE: TAG_NAME
  see '>'      -> emit the completed tag token, go to STATE: TEXT
  see anything  -> keep buffering the tag name, stay in STATE: TAG_NAME

Module 5 builds exactly this, at full size, for real HTML — dozens of states, but each one just as small and explicit as the three above.

Where This Shows Up In The Course

  • Module 5 — the HTML tokenizer is a state machine over characters.
  • Module 7 — the CSS tokenizer is a smaller, differently-shaped state machine.
  • Module 18 — the JS tokenizer is a third, independent state machine (numbers, strings, identifiers, operators each need their own states).
  • Module 17 — the event loop is itself a coarse state machine: idle, running a task, or processing a render — never more than one at once.
🧠 Quick check
Why can't a tokenizer just use one big regular expression instead of a state machine?

Some simple tokenizers can, for simple enough grammars. But HTML has constructs (like comments, or attribute values that may or may not be quoted, or script/style tags whose contents shouldn't be tokenized as HTML at all) where "what counts as the end of this token" depends entirely on what came before it — exactly the kind of context a single regex can't carry, but an explicit state does. This is also why real specs (the WHATWG HTML tokenization algorithm) are written as a state machine, not as a grammar of regular expressions.
