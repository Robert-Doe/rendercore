Bytes & Text Encoding

Everything a browser receives from the network starts as raw numbers. "Text" is an agreement about how to read those numbers, not a different kind of data.

🍽️ The Restaurant

The crate the runner brings back from the warehouse (Module 0's analogy) doesn't have English words stamped on the ingredients — it has numbered bins. "Bin 72" means nothing until the kitchen consults a shared chart that says "bin 72 = the letter H." Every kitchen in the world that uses the same chart can read the same crate the same way.

The Core Idea

A network connection has no concept of "letters." It only ever moves raw 8-bit numbers, called bytes, each between 0 and 255. When your browser receives the byte 72, it is not "the letter H" — it's just the number 72. It only becomes the letter H because both the sender and the receiver agreed, in advance, to use a lookup table called an encoding that maps number 72 to the character H.

The web's standard encoding is UTF-8. In UTF-8, byte values 0–127 map one-to-one to the same characters as the much older ASCII table (so `72` is always `H`, `101` is always `e`). Byte values 128 and above signal "this character needs more than one byte" — UTF-8 uses 2, 3, or 4 bytes to represent characters outside the original ASCII range (accented letters, emoji, non-Latin scripts).

A Worked Example

The text Hi! sent over a TCP connection is, at the wire level, exactly these three bytes:

72  105  33
'H' 'i'  '!'

Nothing about those three numbers is the text "Hi!" — they become "Hi!" only when something on the receiving end (Python's bytes.decode('utf-8'), in this course) runs them through the UTF-8 table. Go the other direction — str.encode('utf-8') — and you turn characters back into the exact bytes a socket can send.

Where This Shows Up In The Course

  • Module 1 — everything a raw socket sends or receives is bytes, never str, until you explicitly decode it.
  • Module 3 — an HTTP response's headers are decoded as text; the body's correct decoding actually depends on a header (Content-Type: ...; charset=...) that the parser has to read first.
  • Modules 5, 7, 18 — every tokenizer (HTML, CSS, JS) operates on already-decoded text, which is only "text" because Module 3 decoded it correctly first.
🧠 Quick check
If a server sends bytes encoded in a Japanese-specific encoding (Shift-JIS) but your code always decodes with UTF-8, what happens?

You get "mojibake" — garbled, wrong characters — or an outright crash (UnicodeDecodeError), because you're reading numbers through the wrong lookup table. The bytes themselves are never wrong; the mismatch between the encoding used to write them and the encoding used to read them is the entire bug. This is exactly why Module 3 reads the Content-Type header before decoding a response body instead of assuming UTF-8 blindly.
