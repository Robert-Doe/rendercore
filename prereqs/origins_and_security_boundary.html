Origins & the Security Boundary

The entire unit of trust on the web is not "the page" and not "the server" — it's a specific triple of scheme, host, and port, called an origin.

🍽️ The Restaurant

Every table gets its own private bill. A waiter serving table 5 is not allowed to walk over and read table 9's bill, add items to it, or hand table 9's receipt to table 5's customer — even though it's the same restaurant, the same waiter pool, the same kitchen. "Which table" is the boundary; nothing about being in the same building crosses it.

The Core Idea

An origin is the exact combination of:

scheme://host:port
https://example.com:443

Two URLs are the same origin only if all three parts match exactly. https://example.com and http://example.com are different origins (different scheme). https://example.com and https://api.example.com are different origins (different host, even though it "looks like" the same site). This is deliberately strict — the whole point is that a script or stored data from one origin should never be silently accessible to another, even a very similar-looking one.

The same-origin policy is the rule, enforced by the browser, that script running in the context of one origin cannot read DOM content, cookies, or storage belonging to a different origin — even if both are open in tabs side by side, at the same instant, in the same browser.

Where This Shows Up In The Course

  • Module 22 — cookies are stored and sent back scoped to the origin (roughly — cookies actually scope slightly looser, by host, which the module calls out explicitly) that set them.
  • Module 23 — builds the actual enforcement: a script's requests to read another origin's DOM/storage are checked against this exact rule and denied.
  • Module 25 — the sandbox broker's policy checks are, in part, origin-aware: what a renderer is allowed to do can depend on which origin it's currently rendering.
🧠 Quick check
Why does changing only the port number (443 vs 8443) count as a different origin, when it's clearly "the same server"?

Because same-origin policy isn't reasoning about which physical server is involved — it's a strict, mechanical, three-part match designed to be impossible to fool with edge cases. If "looks like the same server" were the rule, an attacker could deliberately stand up a look-alike service on a different port and argue it should be trusted with the real origin's cookies and DOM access. Making the match exact and mechanical (scheme + host + port, nothing inferred) removes that judgment call entirely.
