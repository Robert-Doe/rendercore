Processes vs. Threads

A process is a locked room with its own memory. A thread is one of several workers inside the same room, sharing everything in it.

🍽️ The Restaurant

Two line cooks working the same station share the same ingredients, the same cutting board, the same pans — if one of them contaminates something, the other one is instantly affected too, because there was never a wall between them. Two separate food trucks parked next to each other share nothing — no ingredients, no equipment — and a fire in one truck cannot spread into the other, because there's an actual wall (two separate vehicles) between them.

The Core Idea

A process is a running program with its own private memory space, enforced by the operating system — one process literally cannot read or write another process's memory without going through an OS-mediated channel (like a pipe or socket) that both sides explicitly set up. If a process crashes, only its own memory and work are lost.

A thread is a separate execution path within a single process, sharing that process's memory completely with every other thread in it. Threads are cheaper to create and communicate trivially (just read/write the same variables) — but a crash in one thread (or memory corruption it causes) can take down the whole process, because there's no OS-enforced wall between threads in the same process.

The tradeoff this course cares about: isolation costs convenience. Processes are safer to crash and harder to sandbox around; threads are faster to coordinate but share fate completely.

A Worked Example

import multiprocessing

def render_tab(url):
    ... # if this crashes, only this process dies

p = multiprocessing.Process(target=render_tab, args=("https://example.com",))
p.start()   # a genuinely separate OS process, own memory space
p.join()

Compare to Python's threading.Thread, which would run render_tab in the *same* process — sharing memory with everything else, including whatever created it. Module 24 deliberately uses multiprocessing, not threading, because tab isolation specifically requires the OS-enforced memory wall a thread doesn't have.

Where This Shows Up In The Course

  • Module 24 — each tab is its own OS process specifically so one tab's crash can't corrupt another tab's memory.
  • Module 25 — the sandbox broker/target split only means anything because a process boundary is a real, OS-enforced wall — a policy check inside a shared-memory thread could be bypassed by any code with access to that memory; a policy check enforced by a *separate process* cannot be bypassed just by having a bug in the other process.
🧠 Quick check
Why does the sandbox broker in Module 25 have to be a separate process, not just a separate function called from inside the renderer's own code?

Because if the "policy check" were just a function living inside the same process as the untrusted renderer logic, a bug (or malicious code) in that renderer could corrupt memory and simply skip the function, or overwrite its logic entirely — there'd be no OS-enforced wall stopping it. Putting the policy check in a genuinely separate process means the renderer physically cannot touch the broker's memory or code at all — the only way to reach it is through the narrow, explicit communication channel (a pipe) that the broker controls on its own terms.
