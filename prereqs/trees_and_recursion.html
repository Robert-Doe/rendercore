Trees & Recursive Traversal

A webpage isn't a list. It's boxes inside boxes inside boxes — and the only sane way to process that shape is a function that calls itself.

🍽️ The Restaurant

A ticket for "Table 5" isn't one flat line — it's a table, which has seats, which each have an order, which each have modifications ("no onions"). To read the whole ticket you don't read it top to bottom like a list; you handle "Table 5," and for each seat under it you handle that seat the exact same way you handled the table — by looking at what's nested inside it.

The Core Idea

A tree is a data structure where each item (a "node") can have zero or more children, each of which can have their own children, and so on — with exactly one node (the "root") that has no parent. HTML is naturally tree-shaped: a <div> contains a <p> which contains text and a <span>, and so on, arbitrarily deep.

Recursion is the natural way to process a tree: write a function that handles one node, and for each of that node's children, calls itself on that child. You never need to know how deep the tree goes in advance — the function keeps calling itself deeper until it hits a node with no children (the "base case"), then returns back up.

A Worked Example

Given this tiny tree:

<div>
  <p>Hello</p>
  <p>World</p>
</div>

a recursive "print every tag name, indented by depth" function looks like:

def print_tree(node, depth=0):
    print("  " * depth + node.tag)
    for child in node.children:
        print_tree(child, depth + 1)   # <- calls itself

This exact pattern — visit a node, recurse into its children — is how Module 6 walks the DOM, how Module 9 resolves inherited CSS properties down a tree, and how Modules 11–13 compute each box's position relative to its parent's position.

Where This Shows Up In The Course

  • Module 6 — the DOM itself is the tree; building it means correctly nesting tokens as parents/children.
  • Module 7 — nested selectors and rule blocks parse into a small tree before flattening to a rule list.
  • Modules 10–13 — layout is recursive by nature: a container's size can depend on its children's sizes, and a child's position depends on its parent's position.
  • Module 18 — parsed JS code becomes an Abstract Syntax Tree (AST); the interpreter evaluates it the same recursive way.
🧠 Quick check
What stops a recursive tree-walking function from running forever?

The base case — a node with no children simply doesn't recurse further, so the function returns instead of calling itself again. A tree by definition has no cycles (a node can never be its own ancestor), so as long as you only ever recurse into children, the recursion is guaranteed to terminate. (Real HTML parsers do have to defend against malformed input that tries to create a cycle — that's part of what Module 6's "recovering from malformed HTML" logic guards against.)
