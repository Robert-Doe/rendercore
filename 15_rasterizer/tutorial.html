What Happens, Step by Step

  1. Create a real Tk window and a real Canvas widget inside it.
  2. Walk Module 14's display list front to back, IN ORDER — the rasterizer never reorders anything; ordering was already decided.
  3. For each DrawRect: call canvas.create_rectangle(..., fill=color, outline="") — a filled box, no border.
  4. For each DrawBorder: call the SAME Tk method, but with fill="" and outline=color instead — an outline, no fill.
  5. For each DrawText: call canvas.create_text(...).
  6. Force Tk to actually process everything (root.update()), then query the canvas back to confirm what's really there.

A Map of Command → Tk Call

DrawRect(x=0,y=0, w=200,h=200, color=gray) │ ▼ canvas.create_rectangle(0, 0, 200, 200, fill="gray", outline="") │ ▼ a REAL item now exists inside Tk's own canvas state — queryable: canvas.type(item) -> "rectangle" canvas.coords(item) -> [0.0, 0.0, 200.0, 200.0] canvas.itemcget(item,"fill") -> "gray" DrawBorder(x=60,y=60, w=20,h=20, color=purple, border_width=3) │ ▼ canvas.create_rectangle(60, 60, 80, 80, fill="", outline="purple", width=3) │ ▼ canvas.type(item) -> "rectangle" (SAME Tk primitive) canvas.itemcget(item,"outline") -> "purple" canvas.itemcget(item,"fill") -> "" (this is what makes it a border, not a fill)

two different display-list command types collapse onto ONE Tk primitive, distinguished only by which of fill/outline is set

The Code, Explained

The whole rasterizer is a dispatch on command type, each branch a one-line call into Tk:

rasterizer.py
if isinstance(cmd, DrawRect):
    item_id = canvas.create_rectangle(
        cmd.x, cmd.y, cmd.x + cmd.width, cmd.y + cmd.height,
        fill=cmd.color, outline="",
    )
elif isinstance(cmd, DrawBorder):
    item_id = canvas.create_rectangle(
        cmd.x, cmd.y, cmd.x + cmd.width, cmd.y + cmd.height,
        fill="", outline=cmd.color, width=cmd.border_width,
    )

Notice both branches call the exact same Tk method — create_rectangle — with different keyword arguments. Tk doesn't have a separate "border rectangle" object; a filled shape and an outlined shape are the same primitive used two different ways.

⚠ Getting a blank or broken result?
  • TclError: no display name (Linux/headless servers): Tkinter needs a display server (X11/Wayland) or a virtual one (like Xvfb) to create even a withdrawn window — this is a real environment requirement, not a bug in this module.
  • Colors or coordinates look off by a pixel when eyeballing a real window: that's likely bbox()'s ~1px padding being confused for the actual draw position — use coords() for the ground truth, as this module's own checks do.

Brain Exercise

🧠 Think before you reveal

This module's checks call root.update() before inspecting any canvas state. What SPECIFIC check in this module's output would be at real risk of failing (not by ordering, but by seeing stale data) if that line were removed?

Reveal the answer

Every single one of the `canvas.coords()` / `canvas.type()` / `canvas.itemcget()` calls are at risk — not because the ITEMS wouldn't exist (Tkinter's `create_rectangle` does register the item immediately), but because Tk's rendering and internal state updates are tied to its event loop. Without giving that loop a chance to run (`root.update()`, or a real running `mainloop()`), some derived state Tk computes lazily could be queried before it's finalized. This module's checks happened to pass reliably with `update()` present precisely because it forces Tk to fully process everything pending before the very next line of Python runs — removing it turns a reliable check into one that depends on timing, which is exactly the category of bug this course's "run it and verify real output" discipline exists to catch before it ships.

There Are No Dumb Questions

Why does `canvas.bbox()` return different numbers than what was actually drawn?
This was tested directly during this module's development: `bbox()` pads its result by roughly 1 pixel on each side, even for a shape with `outline=""` and no visible border — it's Tk's own selection/hit-testing margin, not a measurement of the visible pixels. `coords()` returns the exact values passed to `create_rectangle`, which is why this module's verification uses `coords()`, not `bbox()`.
Could this module export an actual image file, not just an in-memory canvas?
Yes — `canvas.postscript(file="out.ps")` is a real Tk capability (verified directly: it produces a genuine, non-empty PostScript file describing everything drawn), with no extra libraries needed. Converting that PostScript to a PNG would need an external tool like Ghostscript, which is why this module doesn't include that extra step — but the PostScript export itself works with nothing beyond what's already imported here.
Is `root.withdraw()` something a real browser would ever do?
Not in normal operation — a browser's whole purpose is a visible window. It's used here purely so this module's checks can run automatically, without a person watching a window pop up and disappear. DECISIONS.md calls this out explicitly so it isn't mistaken for how Module 21's actual chrome UI will behave.
