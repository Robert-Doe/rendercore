Stacking & a Flexbox Subset

Two questions normal block flow never has to answer: how should leftover space be shared, and who paints on top of whom?

📄 Companion doc: DECISIONS.md · Source: flex_and_stacking.py

Prerequisites

The Big Analogy

🍽️ The Restaurant, continued

Flexbox is a caterer with a fixed-length buffet table and dishes of different declared "importance" — a dish marked "importance 2" gets served twice as much of whatever extra table space is left over as a dish marked "importance 1." A dish marked "importance 0" gets exactly the space it asked for and not one inch more, no matter how much table is left empty.

Stacking is a completely different question: when two plates physically overlap on the table, which one is on top? The kitchen doesn't just go by which plate was set down first (order of arrival) — each plate can carry an explicit "stack me higher" priority tag, and only when two plates have the exact same tag does arrival order settle it.

What Happens, Step by Step

  1. Flex: sum every item's basis (declared) width. Subtract that from the container's width to get the free space.
  2. Sum every item's flex-grow value.
  3. For each item, its share of the free space is free_space × (its flex-grow ÷ total flex-grow) — zero if flex-grow is 0, or if nothing in the row grows at all.
  4. Place items left to right, each one's width equal to its basis plus its share.
  5. Stacking: assign every overlapping element its z-index (or treat "auto" as 0) and its position in document order.
  6. Sort by z-index first — lowest painted first (furthest back). Only when z-index ties does document order decide, later-in-document painting on top.

A Map of Both Algorithms

FLEX — container width 600, basis 100/100/100, grow 1:2:1 total_basis = 300 free_space = 600 - 300 = 300 total_grow = 4 left: extra = 300 * 1/4 = 75 -> width = 175 center: extra = 300 * 2/4 = 150 -> width = 250 right: extra = 300 * 1/4 = 75 -> width = 175 175 + 250 + 175 = 600 (exact) STACKING — sort key (z_index, tree_order), z_index dominant items: A(z=2,#0) B(z=auto,#1) C(z=-1,#2) D(z=2,#3) E(z=0,#4) sorted: C(z=-1) < B(z=0,#1) < E(z=0,#4) < A(z=2,#0) < D(z=2,#3) \_______/ \_____________________/ \_______________/ most negative z=0 GROUP, tied z=2 GROUP, tied z first -> DOM order -> DOM order breaks it breaks it

flex distributes SPACE proportionally; stacking distributes PAINT ORDER, z-index-first

The Code, Explained

Flex's entire distribution formula is one line, and it's a straight ratio — not a boolean "does it grow":

flex_and_stacking.py
extra = (free_space * item.flex_grow / total_grow) if total_grow > 0 else 0.0

Stacking's entire ordering rule is one sort key, structurally identical to Module 9's cascade tie-break — z first, document order only as the tie-breaker:

flex_and_stacking.py
def sort_key(item):
    z = item.z_index if item.z_index is not None else 0
    return (z, item.tree_order)

⚠ Getting a blank or broken result?
  • All flex items get equal extra space regardless of flex-grow: check the formula uses `item.flex_grow / total_grow`, not just splitting `free_space` evenly across the item count.
  • Paint order matches document order even with different z-index values: check the sort key tuple has `z` FIRST — `(tree_order, z)` would sort by document order first and silently ignore z-index almost entirely.

Brain Exercise

🧠 Think before you reveal

Suppose `free_space` were NEGATIVE — the items' total basis width is larger than the container (they overflow). What does `layout_flex_row`'s current code actually do in that case, and is it correct real flexbox behavior?

Reveal the answer

free_space = max(0.0, container_width - total_basis) clamps it to exactly 0.0 whenever basis exceeds the container — so every item simply keeps its basis width, and the row overflows the container rather than the code producing a negative extra value (which would incorrectly SHRINK items that have a positive flex-grow but no flex-shrink logic to apply). This happens to avoid a crash or nonsensical negative width, but it is NOT full flexbox correctness: real flexbox has `flex-shrink` specifically to handle this overflow case by proportionally shrinking items, which this module explicitly does not implement (see DECISIONS.md, Part A). So: safe, but incomplete — exactly the kind of distinction this course's "Limits" sections exist to keep visible rather than papered over.

There Are No Dumb Questions

Why are flexbox and stacking in the same module — aren't they unrelated?
They're unrelated mechanically, but they share a category: both are things that happen OUTSIDE the block-stacking, top-to-bottom flow Module 11 builds. Flexbox is an alternative layout mode for arranging children; stacking is a paint-order concern that applies regardless of which layout mode positioned the elements. Grouping them acknowledges "not normal flow" as the connecting idea, while being honest in the code that they're two independent algorithms, not one shared one.
Does a higher z-index always mean an element is "more visible"?
It means an element paints LATER, which usually means more visible where it overlaps something with a lower z-index — but only within the same stacking context. This module's simplification (treating everything as one flat context) is exactly why DECISIONS.md flags nested stacking contexts as unimplemented: in real CSS, a z-index of 9999 inside one stacking context can still end up visually BELOW a z-index of 1 in a different, higher-level stacking context — a genuinely common source of real-world confusion this module doesn't yet model.
Why does document order matter at all for stacking, if z-index is what really controls it?
Because most real elements never set z-index explicitly — they're all effectively "auto"/0, tied with each other. Without a document-order tie-break, painting order for the vast majority of ordinary overlapping content (like normally-flowed elements that happen to overlap via negative margins) would be undefined. Document order as the tie-break is what makes "later in the HTML paints on top" the sensible, predictable default it is in real browsers.
