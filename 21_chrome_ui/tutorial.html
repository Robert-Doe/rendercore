The Big Analogy

🍽️ The Restaurant, continued

A table's server keeps a running paper strip of every dish that's been brought to that table tonight, in order, plus a pin marking which one is CURRENTLY in front of the guest. "Bring the previous one back" moves the pin left; "bring the next one" moves it right. But if the guest asks for something totally different while the pin is sitting in the middle of the strip — every dish that was ahead of the pin gets torn off and thrown out. There's no version of "go forward" anymore to something that's been physically discarded — that's not a missing feature, it's just what happens when you order something new instead of continuing down a path you already left.

What Happens, Step by Step

  1. User (or a script) calls go(url). The URL is parsed (Module 2) to decide http vs. https.
  2. A real fetch happens — Module 3 for http, Module 4 for https — over the real network.
  3. The real response's <title> is pulled out using Module 5's real tokenizer.
  4. Before adding this new page to history, EVERYTHING past the current position is discarded — any abandoned "forward" pages are gone.
  5. The new page is appended, and the current-position pointer moves to it.
  6. back()/forward() just move that pointer — they never fetch anything new, and never touch the list's contents.

A Map of a Navigation Sequence

go(example.com) entries: [example.com] index: 0 go(info.cern.ch) entries: [example.com, info.cern.ch] index: 1 back() entries: [example.com, info.cern.ch] index: 0 (unchanged list!) go(https://example.com) TRUNCATE entries[1:] first -> [example.com] THEN append -> [example.com, https://example.com] index: 1 info.cern.ch is now GONE from the list entirely — not just unreachable, actually discarded. forward() from here returns None.

the truncation happens BEFORE the append — reversing that order is the classic history bug

The Code, Explained

The entire correctness of this module rests on the ORDER of two lines:

chrome_ui.py
def push(self, entry):
    self.entries = self.entries[: self.index + 1]   # 1. discard abandoned forward entries
    self.entries.append(entry)                        # 2. THEN add the new one
    self.index += 1

Swap these two lines and the new entry would get discarded along with the old forward history, or the truncation would happen a step too late — either way, a real, observable navigation bug.

Reusing Module 5 for something this module never expected to need is worth pointing at directly:

chrome_ui.py
tokens = tokenize(html)   # Module 5, completely unmodified
for i, tok in enumerate(tokens):
    if isinstance(tok, StartTag) and tok.name == "title":
        if i + 1 < len(tokens) and isinstance(tokens[i + 1], Text):
            return tokens[i + 1].data.strip()

Limits / What You Cannot Do Yet

Can't do yet

  • Actually RENDER a fetched page — this module only fetches and tracks history, doesn't connect to Modules 6-16
  • Multiple simultaneous tabs sharing one window (each `BrowserTab` here is standalone)
  • Persist history across restarts — it lives only in memory, for one run

Can do now

  • Navigate to real pages over real network connections, http and https both
  • Correctly maintain back/forward history, including the truncation case most implementations get wrong on a first try
  • Safely handle navigating past either end of history without crashing

⚠ Getting a blank or broken result?
  • History keeps growing instead of truncating: check `push()` slices `entries[: self.index + 1]` BEFORE appending, not after.
  • info.cern.ch fetch fails: it's a real, historically significant but small site — confirm outbound HTTP (not just HTTPS) traffic isn't blocked on your network.
  • Title comes back (untitled): check the page actually has a `<title>` tag whose very next token is a `Text` token — a comment or attribute sitting between them would break this simple lookup (a real, named limitation, not handled by this module).

Brain Exercise

🧠 Think before you reveal

Suppose `push()`'s two lines were swapped — append first, THEN truncate to `entries[: self.index + 1]`. Trace through this module's exact test sequence and figure out what `tab.history.entries` would contain right after the `https://example.com` navigation. Would the bug be obvious or subtle?

Reveal the answer

Genuinely subtle, not obvious — that's what makes this a real bug worth naming. At the point of the third navigation, index is 0 (after the earlier back()). Appending first would make entries temporarily [example.com, info.cern.ch, https://example.com] (length 3). THEN truncating to entries[: self.index + 1] — but `self.index` is still 0 at this point in a swapped version, since it hasn't been incremented yet — would slice down to entries[:1], i.e. just [example.com], DISCARDING the new page you just tried to navigate to along with the old one! The final result would show only 1 history entry, with the CURRENT page (the one just visited) missing entirely — a much stranger, harder-to-diagnose symptom than "forward history didn't clear," because the bug report would be "my address bar shows a page that isn't in my history at all."

There Are No Dumb Questions

Why fetch info.cern.ch specifically, instead of just using two example.com URLs?
Partly to prove the fetch is genuinely hitting different real content (not a coincidence of caching or a hardcoded fixture), and partly because it's a nice, real, historically meaningful page to have this course's own from-scratch browser successfully load — the actual first website, still online, served the same simple way it always has been.
Why does `back()`/`forward()` never re-fetch the page over the network?
Because the response is already stored in the `HistoryEntry` from when it was originally fetched — navigating history is a LOCAL operation on already-known data, not a new network request. (Real browsers do sometimes re-fetch on back/forward, depending on caching headers and whether the page opted out of being cached in history — a real nuance this module's simpler model doesn't need to handle.)
Is `can_go_forward()` returning `True` right after a `back()` call obvious, or does it deserve its own check?
It deserves its own check specifically because it's the thing that's WRONG in a broken implementation right up until the next navigation happens — a version of this code with the truncation bug would ALSO report `can_go_forward() == True` correctly at this exact point, only breaking once a new page is visited. Testing intermediate states, not just final ones, is what catches bugs whose symptoms only appear one step later.
