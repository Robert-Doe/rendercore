The Cascade

Three rules all claim to set the same color. Exactly one of them is allowed to win — and the rule for deciding which is completely deterministic.

The Big Analogy

🍽️ The Restaurant, continued

Three different pages of the house style guide all claim to say what sauce goes on this dish: the general "all soups" page, the more specific "soups with a garnish" page, and a handwritten sticky note on today's ticket that says "no, seriously, use the red sauce, I don't care what the book says." The sticky note (!important) wins outright, no matter how official-looking the book pages are. Absent a sticky note, the more specific page (the one that had to know more about this exact dish to apply) wins over the general one. And if two pages are equally specific and disagree, the chef trusts whichever one was literally photocopied into the binder last — the most recently stated instruction, all else being equal.

What Happens, Step by Step

  1. For a node, gather every declaration from every matching rule (Module 8), tagging each with the specificity of whichever selector in that rule actually matched, and the rule's position in the stylesheet.
  2. Group these candidate declarations by property name — color's candidates are considered separately from border's.
  3. For each property, split its candidates into two pools: !important ones and normal ones. If ANY important candidate exists, normal ones are ignored entirely for that property.
  4. Within the chosen pool, pick the candidate with the highest specificity. If there's a tie, pick whichever appeared LATER in the stylesheet.
  5. That's the node's own "specified" style. For any inheritable property (like color) still unset after that, copy the value down from the parent's already-computed style.
  6. For anything still unset, fall back to a hardcoded initial value.

The Code, Explained

The entire tie-breaking rule is one sort key:

cascade.py
important_cands = [c for c in cands if c[2]]
pool = important_cands if important_cands else cands
best = max(pool, key=lambda c: (c[0], c[1]))

Two separate ideas live in these three lines: importance is a pool selection (an all-or-nothing filter, decided before comparing anything else), while specificity-then-order is a single sort key where Python's tuple comparison does the "compare the first thing, only look at the second on a tie" work for free.

Inheritance is a strict top-down walk, because a child can't inherit from a parent that hasn't been resolved yet:

cascade.py
def _walk(node, parent_style):
    style = compute_style(node, rules, parent_style)
    result[id(node)] = style
    for child in node.children:
        if isinstance(child, Element):
            _walk(child, style)   # <- the CHILD call gets the PARENT's finished style

Limits / What You Cannot Do Yet

Can't do yet

  • Full CSS inheritance/initial-value tables — only a small demo subset is defined
  • Any layout — computed styles exist, but nothing has a position or size yet
  • Shorthand properties (margin: 10px 5px expanding into four longhand values)

Can do now

  • Resolve conflicting declarations by specificity, with correct source-order tie-breaking
  • Correctly let !important override even the highest specificity
  • Correctly inherit values down the tree, and correctly NOT leak non-inherited properties
  • Fall back to sensible defaults when nothing set a property at all

⚠ Getting a blank or broken result?
  • Later-declared, lower-specificity rules always win: check the sort key is (specificity, order), not just order alone.
  • !important doesn't override a high-specificity id selector: confirm the important/normal split happens BEFORE the specificity comparison, as two separate pools — not as an extra point added to specificity.
  • Every child ends up with its parent's border, padding, etc.: check INHERITED_PROPERTIES — only specific properties should copy down; most shouldn't.

Brain Exercise

🧠 Think before you reveal

Two rules both apply !important to the same property on the same element, with DIFFERENT specificities. Trace through compute_style(): does specificity end up mattering after all, in this specific scenario?

Reveal the answer

Yes — and this is worth sitting with, because it shows importance and specificity aren't actually in total opposition; importance is a pool filter, and specificity is the tie-break within whichever pool is active. If both candidates are important, important_cands contains both of them, and pool = important_cands. Then max(pool, key=lambda c: (c[0], c[1])) still compares their specificities against each other, exactly as it would for two normal declarations — specificity is never "turned off," it's just evaluated within a smaller, important-only pool once any important declaration exists for that property. So: among important declarations, specificity (then order) still decides. Among a mix of important and normal, importance alone decides regardless of specificity. Both statements are true at once, and the two-line pool selection followed by one sort key is what makes them both true from the same code.

There Are No Dumb Questions

Why is `border` a bad example of an inherited property, but `color` a good one?
This mirrors real CSS's actual design, not an arbitrary choice this module made: a border drawn around a `
` visually wrapping text inside it would look wrong if every nested `` also drew its own border — borders are about a specific box, not about content in general. Text color, font, and text alignment are about how content reads, which naturally makes sense to flow down into nested content unless something more specific overrides it. The spec's inherited-property list generally follows this "is this about the box, or about the content" distinction.
Could a property have zero candidates, not even an initial value?
In this module, yes — `INITIAL_VALUES` only covers four properties. Query `styles[id(node)]['margin']` on a node with no matching margin rule and you'd get a `KeyError`, since neither the cascade nor inheritance nor the initial-value table ever set it. Real CSS defines an initial value for literally every property so this never happens; this module's table is explicitly a starting subset (DECISIONS.md), and Module 10 will need to grow it.
Does source order ever matter when specificities are clearly different?
No — and this is the most common real-world CSS misunderstanding this module's Case 1 is designed to correct. "The last rule in the file wins" is only true when specificities are exactly tied; a highly specific rule declared first in the file still beats a low-specificity rule declared last, every time, as Case 1 demonstrates directly.
