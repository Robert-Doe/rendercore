HTTP Header Injection Prevention

No HTML. No script. No browser even required for the attack itself — two bytes, `\r\n`, are the entire vulnerability.

📄 Companion doc: DECISIONS.md · Source: header_injection.py

Prerequisites

Module 3: HTTP/1.1 From Scratch

The Big Analogy

🍽️ The Restaurant, continued

A ticket printer separates each instruction with a line break — one instruction per line, always. If a guest's freely-typed note ("no onions, please") is pasted directly onto the ticket and that note happens to CONTAIN a line break followed by something that looks like a real instruction ("no onions\ncomp this whole table's bill"), the printer has no way to tell the difference — it just sees two lines, both formatted exactly like real instructions, because line breaks are ALL that separates one instruction from the next.

What Happens, Step by Step

  1. A server takes some untrusted input (a cookie value, a query parameter) and reflects it into one of its OWN response headers.
  2. If that input contains a raw \r\n (CRLF), and it's inserted without sanitization, the resulting raw response bytes now contain what LOOKS like a real header boundary — because CRLF is the header boundary, to any parser, real or forged.
  3. A real client (Module 3's parse_response) receives these bytes over a real socket and splits the header block on \r\n, exactly as it's supposed to — with no way to know one of those lines was smuggled in.
  4. The forged header(s) — including, in this module's demo, a fake Set-Cookie — end up in the client's parsed headers dict, indistinguishable from genuine ones.
  5. Stripping \r/\n from the untrusted value BEFORE it's inserted removes the only character sequence that could ever be mistaken for a header boundary — the payload survives, intact, as one line.

A Map of the Raw Bytes

UNSANITIZED — raw bytes actually sent over the socket: HTTP/1.1 200 OK\r\n Content-Type: text/plain\r\n Content-Language: en\r\n X-Injected: true\r\n <- attacker's payload, now its OWN header line Set-Cookie: admin=true\r\n <- and this one too — a REAL forged cookie Content-Length: 5\r\n \r\n hello Module 3's parse_response() sees FIVE headers, all "real": {content-type, content-language, x-injected, set-cookie, content-length} SANITIZED — \r\n stripped from the value first: Content-Language: enX-Injected: trueSet-Cookie: admin=true\r\n Module 3's parse_response() sees ONE content-language header, its value an ugly but harmless, structurally inert single line.

the exact same information, the exact same characters — only whether they form a NEW LINE decides whether it's an attribute value or an attack

The Code, Explained

The entire fix is two `.replace()` calls:

header_injection.py
def sanitize_header_value(value: str) -> str:
    return value.replace("\r", "").replace("\n", "")

And the proof runs the attack against a REAL client, over a REAL socket — not a string comparison:

header_injection.py
sock.sendall(b"GET / HTTP/1.1\r\n...")
response = parse_response(sock)   # Module 3, completely unmodified
"x-injected" in response.headers   # True, for the unsanitized case

Limits / What You Cannot Do Yet

Can't do yet

  • Reject the whole request/response outright (this module strips; a production system might prefer a hard 400 error — see DECISIONS.md)
  • Prevent request-header injection (client → server) — this module targets the more dangerous response direction only

Can do now

  • Prevent a real, end-to-end response-splitting attack, verified against a real client over a real socket
  • Preserve the attacker's full payload as harmless data rather than silently dropping it

Brain Exercise

🧠 Think before you reveal

This module strips `\r` and `\n` independently, anywhere they appear. Would stripping only the literal two-character SEQUENCE `"\r\n"` (and leaving a lone `\r` or lone `\n` alone) be equally safe?

Reveal the answer

Not necessarily — and this is a real, historically relevant nuance. Different HTTP implementations have, at various points, been more lenient than the spec technically allows, sometimes treating a LONE `\n` (without a preceding `\r`) as a valid line terminator on its own — a compatibility accommodation for non-conforming clients/servers. If the sanitizer only stripped the exact two-character sequence `"\r\n"`, a payload containing just `"\n"` alone could still be treated as a line break by a lenient downstream parser, even though this module's OWN `sanitize_header_value` would have left it untouched by design. Stripping `\r` and `\n` INDEPENDENTLY, regardless of whether they appear together, removes both characters that any real-world HTTP implementation might treat as a line terminator — a stricter, safer choice specifically because it doesn't assume every downstream parser agrees on what counts as "a real line break."

There Are No Dumb Questions

Is this really an "XSS" module, or a different category of bug?
A different but closely related category — this course groups it into the same "encoders and sanitizers" phase because the underlying pattern is identical: untrusted data crossing into a context with its own syntax (HTTP headers, delimited by CRLF) without being neutralized first. The consequence here (forged headers, potentially a forged Set-Cookie or a fully split, attacker-controlled second response) is different from script execution, but the root cause and the fix shape are the same lesson repeated at a different layer.
