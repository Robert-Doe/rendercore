HTML Entity Encoding

The exact same tokenizer that turns real HTML into real tags will turn an unescaped `<script>` in a comment field into a real, running script.

📄 Companion doc: DECISIONS.md · Source: entity_encoding.py

The Big Analogy

🍽️ The Restaurant, continued

A comment card asks guests to write feedback in plain text. If the kitchen photocopies a guest's comment DIRECTLY onto next week's printed menu without checking it first, and a guest wrote something that LOOKS like a menu-formatting instruction ("NEW SECTION: Free desserts for everyone"), it would print as if it were a real, intended part of the menu — because the photocopier can't tell "text a guest wrote" from "real menu structure" once they're both just ink on the same page. The fix is spelling out anything comment-card-shaped in a way that can never be mistaken for a formatting instruction, no matter what it says.

What Happens, Step by Step

  1. Untrusted text (a comment, a search query, a username) is about to be inserted into HTML body content.
  2. Walk through the text one character at a time. For each of five specific characters (& < > " '), substitute its named entity instead of the literal character.
  3. Every other character passes through completely unchanged — encoding never touches or reorders the SAFE parts of the text.
  4. Splice the encoded result into the HTML. Because the actual < character never appears, Module 5's tokenizer can never transition into tag-parsing state from anywhere inside it.
  5. The browser displays the ORIGINAL text, character for character — &lt;script&gt; renders on screen as the literal, inert text <script>, not as a tag.

A Map of the Tokenizer's Real Behavior

payload: <script>alert(document.cookie)</script> UNENCODED, fed to Module 5's tokenize(): [ StartTag('script'), Text('alert(document.cookie)'), EndTag('script') ] ^^^^^^^^^^^^^^^^^^ a REAL tag token — a browser would RUN this ENCODED first (<script>...), fed to the SAME tokenize(): [ Text('&lt;script&gt;alert(document.cookie)&lt;/script&gt;') ] ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ ONE inert text token — no tag ever begins, because no real '<' character exists anywhere in the input

the difference between "executes" and "just text on screen" is exactly one character: a real, literal <

The Code, Explained

Per-character lookup, not chained replacements — this is what makes the classic ordering bug structurally impossible, not just avoided:

entity_encoding.py
def encode_html_entities(s: str) -> str:
    return "".join(ENTITY_MAP.get(ch, ch) for ch in s)

And the actual proof — not a claim, a real query against Module 5's real tokenizer:

entity_encoding.py
def has_real_tag(html: str, tag_name: str) -> bool:
    return any(isinstance(tok, StartTag) and tok.name == tag_name
               for tok in tokenize(html))

Limits / What You Cannot Do Yet

Can't do yet

  • Safely encode text for an HTML ATTRIBUTE context — different rules apply (Module 28)
  • Safely encode text for a <script> or CSS context — neither is covered here
  • Strip or allow SPECIFIC tags in genuinely-HTML content — this module only ever fully neutralizes markup, never partially permits it (Module 30)

Can do now

  • Guarantee untrusted body text can never become a real tag, verified against the real tokenizer
  • Correctly identify which of the five encoded characters is actually load-bearing for THIS context
  • Avoid a real, classic double-encoding bug by construction
