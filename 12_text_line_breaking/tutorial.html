Text Layout & Line Breaking

A browser never asks "how do I wrap text beautifully." It asks "does the next word fit — yes or no," over and over, left to right.

📄 Companion doc: DECISIONS.md · Source: text_layout.py

Prerequisites

Coordinate Systems & the Box Idea Module 11: Block & Inline Layout

The Big Analogy

🍽️ The Restaurant, continued

Think of a menu board with a fixed physical width, and someone writing today's specials on it one word at a time, left to right. They never plan the whole sentence in advance — they just keep asking "does the next word still fit on this line?" The moment the answer is no, they move the chalk to the start of the next line and keep going from there. They never erase and rewrite an earlier line to make things look more even — that would be a fundamentally different (and slower) way of writing the board, the kind a professional typesetter does for a printed book, not what a menu board writer does every single morning.

What Happens, Step by Step

  1. Split the text into words on whitespace.
  2. Start an empty current line, width 0.
  3. For each word: would adding it (plus a space, if the line isn't empty) push the line's width past max_width?
  4. If yes AND the line already has at least one word: close the current line, start a new one with just this word.
  5. Otherwise: add the word to the current line, whether it technically "fits" or not (an empty line must always accept at least one word, even an over-wide one — see step 6).
  6. After all words are placed, assign each line a real (x, y): same x for every line, y increasing by one line-height per line — the inline equivalent of Module 11's block-stacking cursor.

A Map of the Wrapping Decision

max_width = 100, char_width = 10 (so "World" = 5 chars = 50px) word "Hello" (50px): line empty -> always accept. line=[Hello] width=50 word "World" (50px): add = space(10)+50 = 60. 50+60=110 > 100 -> BREAK. new line=[World] width=50 word "this" (40px): add = 10+40 = 50. 50+50=100, NOT > 100 -> fits. line=[World, this] width=100 word "is" (20px): add = 10+20 = 30. 100+30=130 > 100 -> BREAK. new line=[is] width=20 ... RESULT: ["Hello"], ["World", "this"], ["is", "a", "test"], ["of"], ["wrapping"]

one decision, repeated: does the next word fit? never a decision that looks backward at earlier lines

The Code, Explained

The entire algorithm is one loop with one condition:

text_layout.py
for word in words:
    word_width = measure_fn(word)
    add_width = word_width if not current else space_width + word_width

    if current and current_width + add_width > max_width:
        lines.append(current)
        current = [word]
        current_width = word_width
    else:
        current.append(word)
        current_width += add_width

Notice if current and ... — the break only triggers when the current line already has something in it. An empty line always accepts the next word regardless of width, which is exactly what guarantees Case 2 (an over-wide word) can never cause an infinite loop.

Limits / What You Cannot Do Yet

Can't do yet

  • Measure real text width — uses a fixed-width stand-in, not actual font metrics
  • Justify text (stretch spaces to make both edges flush)
  • Break mid-word (hyphenation) for a word that doesn't fit
  • Mix text with other inline elements (bold spans, links) on the same line

Can do now

  • Correctly wrap real text into lines at any given width
  • Correctly handle a word wider than the container without breaking
  • Correctly reposition lines vertically, stacked by line height

⚠ Getting a blank or broken result?
  • Infinite loop / hangs: check the empty-current-line case still unconditionally accepts a word — if that guard is removed, an over-wide word can never be placed and the algorithm gets stuck deciding it doesn't fit, forever.
  • Every word ends up on its own line: check `add_width` correctly includes `space_width` only when the line isn't empty — always adding a space, even to the first word, would overcount every line's width.

Brain Exercise

🧠 Think before you reveal

Case 1's second line came out as "World this" (100px exactly) rather than stopping after just "World." Given max_width=100, why does a line that lands EXACTLY at the limit count as fitting, rather than being treated as one pixel too many?

Reveal the answer

Because the break condition is strictly current_width + add_width > max_width — using >, not >=. A line that lands EXACTLY at the container's width still fits inside it; it doesn't overflow until it exceeds it. This is a real, meaningful choice (not an off-by-one accident): using >= instead would reject perfectly valid content that happens to use the container's width down to the last pixel, which would be visibly wrong compared to how every real browser actually renders text that fits exactly.

There Are No Dumb Questions

Why not use the more sophisticated line-breaking algorithm word processors use for justified text?
Because that's not what CSS's normal text flow actually specifies, and this course is building what browsers do, not what's theoretically nicest. The Knuth-Plass algorithm (and similar) can produce more visually even paragraphs by looking ahead and sometimes making an earlier line slightly less full to avoid a bad break later — genuinely useful for justified, printed text, but more expensive and not how a browser lays out ordinary unjustified paragraphs.
Is it a real limitation that `fixed_width_measure` treats every character as the same width?
Yes, and it's named as one on purpose (DECISIONS.md) rather than left implicit. The entire reason it's there is so this module's line-break math is checkable by hand before ever running the code — every line grouping in this tutorial was computed on paper first. Because `measure_fn` is a pluggable parameter, swapping in Module 15's real font metrics later requires zero changes to `wrap_words()` itself.
What happens to multiple spaces between words, or a tab character?
text.split() (no arguments) collapses any run of whitespace — spaces, tabs, newlines — into single word separators and discards it entirely, so "a b" (two spaces) and "a\tb" both produce the same two words, "a" and "b". This matches how HTML actually treats whitespace in normal text flow (collapsing runs of whitespace to one space) closely enough for this module's purposes, though real HTML whitespace collapsing has its own more detailed rules this course doesn't implement.
