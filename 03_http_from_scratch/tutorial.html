HTTP/1.1 From Scratch

The Big Analogy

🍽️ The Restaurant, continued

Module 1's runner got away with something sloppy: they waited at the warehouse door until the warehouse worker felt like shutting the door, and treated "door shut" as "crate is fully packed." That only worked because this particular warehouse happened to shut the door right after handing over one crate.

A professional runner doesn't rely on that. A proper packing slip either says "this crate contains exactly 40 items" (Content-Length — count them as they come out, stop at 40, don't wait for anything else) or ships the crate in labeled batches, each batch stamped with its own size, ending with a batch stamped "size zero — that was the last one" (chunked encoding). Either way, the runner knows the crate is complete from the paperwork itself, never from the warehouse door happening to close.

What Happens, Step by Step

  1. format_request() builds the exact bytes of a request line + headers, ending in a blank line, per the HTTP/1.1 grammar.
  2. The request is sent over Module 1's socket via send_all().
  3. _recv_until(sock, b"\r\n\r\n") reads just enough to capture the status line and headers — stopping exactly at the blank line that separates headers from body, however many recv() calls that takes.
  4. The status line and headers are parsed out of that header block.
  5. The response's own framing decides what happens next: a Content-Length header means "read exactly this many more bytes." A Transfer-Encoding: chunked header means "read labeled chunks until a zero-size one." Neither present means fall back to reading until the connection closes — the last resort, not the plan.
  6. The socket is closed, and a fully-parsed HTTPResponse (status, headers, body) is returned — no partial reads, no guessing.

A Map of the Wire Format

REQUEST (sent): GET / HTTP/1.1\r\n Host: example.com\r\n Connection: close\r\n User-Agent: FromScratchBrowser/0.1 (educational)\r\n Accept: */*\r\n \r\n <- blank line: end of headers, no body on a GET RESPONSE (received), Content-Length framing: HTTP/1.1 200 OK\r\n Content-Type: text/html\r\n Content-Length: 137\r\n \r\n <- _recv_until() stops HERE <html>...</html> <- then read EXACTLY 137 more bytes, stop RESPONSE (received), chunked framing: HTTP/1.1 200 OK\r\n Transfer-Encoding: chunked\r\n \r\n 7\r\n <- next chunk is 7 (hex) bytes Hello, \r\n 6\r\n <- next chunk is 6 bytes World!\r\n 0\r\n <- zero-size chunk = end of body \r\n

two different framings, same job: tell the reader exactly when to stop, without relying on the connection closing

The Code, Explained

The precedence check is the single most important control-flow decision in the module:

http_client.py
if "content-length" in headers:
    length = int(headers["content-length"])
    body, _ = _recv_exact(sock, length, leftover)
elif headers.get("transfer-encoding", "").lower() == "chunked":
    body = _read_chunked(sock, leftover)
else:
    # last resort — see DECISIONS.md
    ...

Content-Length is checked first because the spec (RFC 9112 §6.3) defines that precedence explicitly — a response is not supposed to send both in conflict, but if a `Content-Length` is present, it wins. This isn't a guess at "what's more common"; it's copying the spec's own stated order.

The chunked decoder's loop mirrors the wire format almost line for line:

http_client.py
while True:
    size_line, buf = _recv_until(sock, b"\r\n", buf)
    chunk_size = int(size_line.split(b";")[0], 16)   # hex!
    if chunk_size == 0:
        _, buf = _recv_until(sock, b"\r\n", buf)
        break
    chunk_data, buf = _recv_exact(sock, chunk_size, buf)
    body += chunk_data
    _, buf = _recv_until(sock, b"\r\n", buf)          # trailing CRLF after data

Note int(size_line, 16) — chunk sizes are written in hexadecimal, not decimal. This is a real, easy mistake: forgetting the base-16 conversion silently "works" for chunk sizes under 10 (where hex and decimal digits look the same) and then corrupts anything larger, which is exactly the kind of bug that's invisible in a quick test and real in production — one more reason to test against a known chunk size like 7/6 below, not just eyeball it.

Limits / What You Cannot Do Yet

Can't do yet

  • Talk to any https:// URL — this only works over plain, unencrypted HTTP (Module 4)
  • Follow redirects (3xx responses) automatically
  • Reuse a connection for multiple requests (we always ask for, and structure around, one request per connection)

Can do now

  • Send a spec-correct HTTP/1.1 request with the mandatory Host header
  • Correctly parse a response's status, headers, and body
  • Determine the body's end from Content-Length or chunked framing — not from the connection closing

Worth pausing on: the real request in Part 1 came back transfer-encoding: chunked, even though we asked for Connection: close. This is not a fabricated example chosen to justify chunked support — it's what `example.com`'s server (behind Cloudflare) actually sent back on this run. Had `parse_response()` only known how to read-until-closed, it would have gotten this specific real response right by luck (the connection did also close), but Part 2 proves the chunked-decoding logic itself is correct independent of that luck.

⚠ Getting a blank or broken result?
  • ConnectionError: connection closed before body was fully received: the server sent a Content-Length that doesn't match what it actually sent — rare, but possible with misbehaving servers. Try a different URL.
  • Part 2 hangs: the local test server thread didn't start in time — check that port 0 (ephemeral) binding isn't blocked by your OS's firewall for loopback traffic.
  • Different headers than shown above: expected — date, age, and cf-ray change on every real request. What should stay constant: status: 200 OK and a body starting with <!doctype html>.

Brain Exercise

🧠 Think before you reveal

Suppose a buggy server sends both a Content-Length: 13 header AND a Transfer-Encoding: chunked body, and they disagree about the actual length. Given the exact order of the if / elif chain in parse_response(), what does this client do — and is that the safe choice?

Reveal the answer

Because content-length is checked first, this client would call _recv_exact(sock, 13, ...) and treat exactly 13 bytes as the entire body — completely ignoring the chunked framing that follows. If the real chunked data is longer, the leftover bytes are just never read (and are discarded when the socket closes). This is, in fact, the spec-mandated behavior in ambiguous cases like this — RFC 9112 treats a response with conflicting length signals as a request smuggling risk and specifically calls out that implementations should prefer rejecting such responses outright in security-sensitive contexts, rather than guessing which framing is "really" correct. Our client doesn't reject it (that's a real gap Module 25's security discussion revisits), but checking Content-Length first at least matches the spec's stated precedence rather than an arbitrary one.

There Are No Dumb Questions

Why does the chunked decoder need int(size_line, 16) instead of just int(size_line)?
Because chunk sizes are written in hexadecimal in the actual wire format — 7 means 7 either way, but 1a means 26, not "invalid number." Forgetting the base argument doesn't crash on small examples (making it a genuinely sneaky bug) — it silently produces wrong lengths only once a chunk is 16 bytes or larger.
Why parse the status line and headers with plain string splitting instead of a regex?
HTTP's header grammar is genuinely simple enough (each line is `key: value`, separated by CRLF, terminated by a blank line) that str.split/str.partition are sufficient and more readable than a regex would be — unlike HTML (Module 5), which needs a real state machine because its grammar has recursive, context-sensitive structure that headers don't.
Is `iso-8859-1` the right encoding for decoding the header block?
For the header names and structure, yes — RFC 9110 defines header field values as restricted to a byte range that ISO-8859-1 (Latin-1) can always decode without error, which is why real HTTP libraries use it there. The body is a completely separate decoding decision, governed by the Content-Type header's own charset — which is exactly the point made in the bytes & encoding prereq.
Why build a whole local test server just to test 13 bytes of chunked data?
Because a real website's framing choice (Content-Length vs. chunked) can change at any time, isn't something we control, and turned out to actually flip between two runs of this very module during development. A test that depends on a live third party's current behavior isn't really testing our code — it's testing today's internet. The local server pins the input exactly, so "does our chunked decoder work" has one deterministic answer.
