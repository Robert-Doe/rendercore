The DOM XSS Sink: innerHTML vs. textContent

Same string. Same length. Same characters. One function makes it inert. The other makes it code.

📄 Companion doc: DECISIONS.md · Source: dom_xss_sink.py

The Big Analogy

🍽️ The Restaurant, continued

A guest hands staff an index card with writing on it. If it goes on the "read aloud to the room, word for word" pile, whatever's written is just words someone hears — harmless, however strange. If the exact same card instead goes on the "these are today's kitchen instructions, follow them" pile, the exact same words are now COMMANDS someone will act on. The card never changed. Which pile it landed in decided everything.

What Happens, Step by Step

  1. Take one untrusted string containing what looks like an `<img>` tag with a dangerous `onerror` handler.
  2. Route it through set_text() — mirrors real element.textContent = value. It becomes exactly one literal text node. No parser ever sees it as markup.
  3. Route the SAME string through set_inner_html() — mirrors real element.innerHTML = value. It gets tokenized and tree-built by Modules 5/6, UNMODIFIED — the identical machinery that parses the page's own real HTML.
  4. The result: a genuine, structural <img> Element, with a genuine, structural onerror attribute — indistinguishable, in the live tree, from one the page's own developer wrote on purpose.
  5. Route the same string through set_inner_html_sanitized() instead — Module 30's sanitizer runs on the freshly-parsed fragment BEFORE it's attached to the live tree, removing the dangerous attribute before it ever becomes observable.

A Map of One String, Three Outcomes

payload = '<img src=x onerror="alert(document.cookie)">' set_text(el, payload) -> el.children = [ TextNode('<img src=x onerror="alert(...)">') ] ONE literal text node. Never parsed. Completely inert. set_inner_html(el, payload) -> tokenize(payload) -> build_tree(...) <- Modules 5 & 6, UNCHANGED -> el.children = [ Element(tag='img', attrs={'src':'x','onerror':'alert(...)'}) ] A REAL element. A REAL onerror attribute. Genuinely dangerous. set_inner_html_sanitized(el, payload) -> tokenize + build_tree, THEN sanitize_children() BEFORE attaching -> el.children = [ Element(tag='img', attrs={'src':'x'}) ] Still real markup. onerror never makes it into the live tree.

the payload variable is passed unmodified to all three calls — the difference is entirely in what runs it

The Code, Explained

The dangerous sink is dangerous specifically because it's not special — it's the SAME parsing pipeline as everything else in this course:

dom_xss_sink.py
def set_inner_html(el, html):
    fragment_root = build_tree(tokenize(html))   # Modules 5 & 6, completely unchanged
    for child in fragment_root.children:
        child.parent = el
    el.children = fragment_root.children

The fix reorders exactly one thing — WHEN sanitization happens relative to WHEN the fragment becomes part of the live tree:

dom_xss_sink.py
fragment_root = build_tree(tokenize(html))
fragment_root.children = sanitize_children(fragment_root.children)   # BEFORE attaching
el.children = fragment_root.children

⚠ Getting a blank or broken result?
  • set_text() somehow produces an Element: check it isn't accidentally calling `tokenize`/`build_tree` anywhere — the entire safety guarantee depends on it never parsing its input at all.
  • set_inner_html_sanitized() still has onerror: confirm `sanitize_children` runs on `fragment_root.children` BEFORE the `for child in fragment_root.children: child.parent = el` / `el.children = ...` lines, not after.

Brain Exercise

🧠 Think before you reveal

Given everything built across this entire phase (Modules 26-31), if a developer correctly used Module 30's sanitizer on the server side, sending only clean HTML to the browser — but the CLIENT-SIDE JavaScript on that page later took a DIFFERENT piece of untrusted data (say, from the URL fragment, which never even reaches the server) and passed it to a real `innerHTML` assignment directly, unsanitized — would the server-side sanitization have helped at all?

Reveal the answer

Not even slightly — and this is precisely why "DOM-based XSS" is treated as its own named category, distinct from the "reflected" and "stored" XSS Modules 27-30 mostly addressed. Server-side sanitization only ever touches data that passes THROUGH the server. A URL fragment (everything after `#`) is explicitly defined (Module 2) to never be sent to the server at all — client-side script reading it via something like `location.hash` and passing it to `innerHTML` creates a genuine vulnerability the server has no visibility into and no ability to sanitize, no matter how carefully Module 30's logic is applied elsewhere. The fix has to live at the SAME layer as the vulnerability: this exact module's sink, checked at the point where untrusted data (from ANY source — server-reflected, DOM-sourced, doesn't matter) meets an HTML-parsing API.

There Are No Dumb Questions

If `innerHTML` is this dangerous, why does it exist at all — why not just remove it from real browsers?
Because it's also genuinely useful for its intended purpose: inserting TRUSTED, developer-authored markup dynamically (templating, rendering a known-safe component). The danger is specific to passing UNTRUSTED data to it, not to the API existing at all — the same way Module 25's sandboxing bonus didn't argue processes shouldn't exist, just that they need the right boundaries around what untrusted code inside them can do.
Is `set_inner_html_sanitized` a complete real-world fix, or does it inherit Module 30's own limitations?
It inherits them directly and honestly — Module 30's DECISIONS.md already named its own scope limits (a small, illustrative allowlist; no CSS sanitization; comments dropped unconditionally). This module doesn't add new safety beyond what Module 30 already provides; it demonstrates WHERE in the pipeline that safety has to be applied — before attachment to the live tree — which is a real, necessary, but not sufficient-on-its-own piece of a complete defense.
Does this mean `textContent`/`set_text` is always the "correct" choice?
Only when you don't actually need to render real markup — which is true for a huge fraction of real use cases (usernames, comments, search results) and is why "prefer textContent over innerHTML whenever you're inserting plain text" is such common, well-founded real-world advice. The moment a feature genuinely requires rendering user-authored formatting (bold, links), `textContent` can't do the job at all — that's exactly the case Module 30's sanitizer plus `set_inner_html_sanitized` exists for.
