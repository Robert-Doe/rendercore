The Big Analogy

🍽️ The Restaurant

A browser is a restaurant that takes a spoken order and delivers a plated dish. You (the customer) say a name — a URL — to the host stand. From there, the order passes through a strict sequence of stations, and no station can do its job until the one before it has finished.

The runner goes to the supplier's warehouse and brings back the raw ingredients in a sealed crate — this is the networking layer: finding the address, opening a connection, and hauling back raw bytes (the HTML, CSS, images).

The prep cook opens the crate and lays the ingredients out in a structured way the kitchen understands — a tray of chopped vegetables here, a bowl of sauce there. This is the HTML parser turning a flat string of text into a structured tree (the DOM). A separate pastry chef reads the house style guide — same sauce recipe for every "soup" ticket, unless a specific ticket says otherwise — and this is the CSS parser and cascade: parsing the rules, then resolving which rule wins when more than one applies to the same dish.

The line cook arranges everything on the plate — correct portion sizes, correct spacing, nothing overlapping wrong — that's layout. The garnish station adds the final visual details in the right order so the sauce doesn't hide the garnish — that's paint and compositing. The dish reaching the table is the pixels reaching your screen.

A head waiter stands near the table the whole time, listening for the customer to say "actually, hold the onions" mid-meal. The waiter doesn't remake the entire dish — they walk back, tell exactly the right station to redo exactly the affected part, and nothing else. That's the event loop, the JS engine, and the invalidation/re-render pipeline working together.

The restaurant serves many tables at once, each with its own waiter and its own running bill, and a kitchen fire at table 5 does not shut down table 9 — that's tabs and process isolation. And critically: no customer is allowed behind the counter. Every request — "bring me a knife," "let me into the walk-in" — goes through staff who check it against house policy first. That's sandboxing, and it's the subject of this course's bonus Module 25.

What Happens, Step by Step

  1. You type a URL and press Enter. The string gets parsed into scheme, host, port, and path (Module 2).
  2. The hostname is resolved to an IP address by the OS's DNS resolver — a real step, but one this course treats as "hardware" (see DECISIONS.md §2).
  3. A TCP connection is opened to that IP on the right port (Module 1).
  4. If the scheme is HTTPS, a TLS handshake wraps that connection in encryption before anything else is sent (Module 4).
  5. An HTTP request is sent, and a response is received — status line, headers, body — all hand-parsed (Module 3).
  6. The HTML body is tokenized into tags, text, and comments (Module 5), then assembled into a DOM tree (Module 6).
  7. Any CSS is tokenized and parsed into a list of (selector → declarations) rules (Module 7).
  8. Each DOM node is matched against every rule that could apply to it (Module 8), and the cascade picks one winning value per property when rules conflict (Module 9).
  9. Every node gets a box — content, padding, border, margin (Module 10) — and real x/y/width/height coordinates via block, inline, and flex layout (Modules 11–13), including wrapped text lines (Module 12).
  10. The layout tree is flattened into a display list of draw commands (Module 14), which is rasterized onto a canvas (Module 15) with correct stacking order for overlapping elements (Module 16).
  11. The page is now visible. The event loop starts, listening for clicks and key presses without blocking rendering (Module 17).
  12. Any embedded scripts run in a from-scratch JS interpreter (Module 18), which can read and mutate the real DOM through explicit bindings (Module 19) — triggering steps 8–10 again, but only for what actually changed (Module 20).
  13. Chrome UI wraps the whole thing: address bar, tabs, back/forward history (Module 21).
  14. Cookies and storage persist state across requests and reloads (Module 22), scoped by same-origin policy so one site can't read another's data (Module 23).
  15. Each tab runs as its own OS process (Module 24), and every privileged action a renderer wants to take is checked by a policy broker first (Module 25).

The Component Map, Explained

Same boxes as the diagram, one plain-English sentence of "what this thing's job is" for each:

ComponentIts one job
Networking stackTurn a hostname into a live, byte-carrying connection to a real server, encrypted if needed.
URL parserSplit a typed string into the pieces (scheme, host, port, path) every other component needs.
HTML parserTurn a flat string of markup into a tree structure the rest of the browser can walk.
CSS parserTurn stylesheet text into a structured list of "if you match this selector, apply these properties" rules.
Style / cascade resolverFor every DOM node, pick exactly one final value per CSS property, even when several rules disagree.
Layout engineConvert "this element is a block, 400px wide, with a 10px margin" into an actual x, y, width, height on the page.
Paint systemTurn "a box at (40, 120), 200×40, red background" into an ordered list of primitive draw instructions.
Compositor / rasterizerExecute the draw instructions in the right visual layering and produce actual pixels.
JS engineRun script code — completely independent of the DOM until something explicitly wires the two together.
DOM–JS bindingsExpose specific, controlled hooks (like getElementById) so script can read/mutate the DOM.
Event loopProcess input and script one task at a time, so rendering never observes a half-finished mutation.
Invalidation pipelineWhen something changes, redo only the affected style/layout/paint steps — not the whole page.
Chrome UIThe part you actually see as "the browser" — address bar, tabs, back/forward — sitting outside any single page.
Cookies / storageRemember state across requests and reloads, scoped to who's allowed to read it.
Same-origin policyStop a script loaded from one site from reading data that belongs to another.
Process modelRun each tab in its own OS process so one tab's crash can't take down the others.
Sandboxing brokerForce every risky action a page's code wants to take through a policy check, instead of trusting it.

Brain Exercise

🧠 Think before you reveal

The network request succeeds. The HTML parses correctly into a full DOM tree. Every CSS rule parses and matches correctly. And yet the page renders as a completely blank white screen. Which single component in the diagram is the most likely place the failure lives — and why isn't it the network, HTML parser, or CSS parser?

Reveal the answer

The layout engine is the prime suspect. Network, HTML parsing, and CSS parsing are all stipulated to have succeeded — the DOM and the parsed rules exist and are correct. But nothing is visible until layout assigns real geometry (x, y, width, height) to each node. If layout produces zero-size or off-screen boxes for everything — a bug in the box model, a recursive layout call that never returns real numbers, a default width miscomputed as 0 — paint and compositing have nothing to draw, and you get a blank page despite every earlier stage being fully correct. This is exactly why Module 10's box model and Module 11's layout math get their own dedicated modules instead of being folded into "CSS stuff": a broken cascade gives you wrong-looking content, but a broken layout gives you no visible content at all.

There Are No Dumb Questions

Is "the rendering engine" the same thing as "the browser"?
No, and this course's two-track split makes the distinction load-bearing. The rendering engine (Track 1, Modules 1–16) is the pure bytes-to-pixels pipeline — it has no concept of tabs, history, or cookies. "The browser" (Track 2) is everything built on top of that engine to make it a usable application. Real-world parallel: Chromium's "Blink" is the rendering engine; "Chrome" is the browser application built around it — and other browsers (older Edge, Opera, Brave) reused Blink as their engine while building a completely different application around it.
Why doesn't DNS get its own module if it's a real, separate protocol?
Every from-scratch course has to draw a line around what counts as "the system we're building" versus "infrastructure we're allowed to stand on." We draw that line at the OS's TCP/IP stack: sockets, DNS resolution, and raw packet delivery are all treated the way an OS course treats the CPU — real, essential, and explicitly not what we're here to build. See DECISIONS.md §2 for the full reasoning.
If the cascade and the CSS parser are both "about CSS," why are they two different modules?
Parsing answers "what rules exist and what do they say." The cascade answers a completely different question: "given that three different rules all claim to set this element's color, which one actually wins?" You can have a perfect parser and still get every displayed color wrong if the cascade's conflict-resolution logic (specificity, source order, !important) is wrong. They're separate failure modes, so they're separate modules (7 and 9), with selector matching (8) as the bridge between them.
Where does the JS engine "live" relative to the DOM — inside it, next to it?
Next to it, and that's deliberate. JavaScript the language (ECMAScript) is specified with zero knowledge of HTML, CSS, or the DOM — you can run a JS engine with no web page in sight (Node.js proves this daily). The DOM is a set of objects the browser chooses to *hand to* the JS engine as a host environment. Module 18 builds a JS interpreter that knows nothing about the DOM; Module 19 is entirely about building the bridge. Keeping them separate mirrors how real engines (V8, SpiderMonkey) are architected — V8 has no idea what a <div> is.
Why is sandboxing a "bonus module" instead of being built into every earlier module?
Two reasons. Pedagogically, you need to understand what a component *does* before you can meaningfully reason about what it should be *prevented* from doing. Architecturally, this actually matches how sandboxing really works in Chromium/Firefox: the rendering and scripting logic doesn't have sandboxing woven through its own code — it runs inside a process that the OS and a separate broker process constrain from the outside. Module 25 builds that outside constraint as its own thing, over the top of everything Modules 1–24 already built, which is structurally honest to how it really works.
