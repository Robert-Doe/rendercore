Block & Inline Layout

A box's POSITION depends on its parent, already known. A box's auto SIZE depends on its children, not known yet. One recursive function has to satisfy both.

📄 Companion doc: DECISIONS.md · Source: block_layout.py

Prerequisites

Coordinate Systems & the Box Idea Trees & Recursive Traversal Module 10: The Box Model

The Big Analogy

🍽️ The Restaurant, continued

Plates get set on a table one at a time, top of the table downward, each new plate going right below the last one's full footprint (including the clear space kept around it). You can place a plate's OWN position the moment you know where the plate before it ended — that's easy, top-down. But if someone asks "how much total table length does this whole table setting take up," you can't answer until every plate on it has actually been placed and you've measured all the way to the last one. Same table, same single pass of setting plates down — but position and total-length are answered at different moments during that one pass.

What Happens, Step by Step

  1. Given a containing block (x, y, width) — where this box's margin box should start, and how wide the space around it is — compute this box's own margin/border/padding, then its content box's x and y.
  2. If width is explicit, use it (adjusted for box-sizing). If it's auto, fill the containing block's width minus this box's own margin/border/padding.
  3. Walk this box's display: block children, IN ORDER. For each one, recursively lay it out at the current vertical cursor position, then advance the cursor by that child's full margin-box height.
  4. Once every child has been laid out (and the cursor has moved past all of them), THAT final cursor position minus the starting position is this box's auto content height — but only if height was auto to begin with.
  5. Return this box's full computed geometry, with its laid-out children nested inside it.

A Map of the Recursion

layout_block(outer, containing_block=viewport) │ │ content_x, content_y computed NOW (needs containing_block — HAVE IT) │ ├─ layout_block(a, cb={x:10,y:10,width:400}) <- position known top-down │ returns a's full box (height=50 explicit) │ cursor_y += a.margin_box_height (70) │ ├─ layout_block(b, cb={x:10,y:80,width:400}) │ │ │ ├─ layout_block(b1, ...) -> height=30 │ │ cursor_y += 30 │ ├─ layout_block(b2, ...) -> height=40 + margin-top 10 │ │ cursor_y += 50 │ │ │ b's own auto content_height = 80 <- ONLY known after b1, b2 returned │ returns b's full box │ cursor_y += b.margin_box_height (94) │ outer's own auto content_height = 70 + 94 = 164 <- ONLY known after a, b returned returns outer's full box

position flows down the left margin of this diagram; auto-height answers bubble up the right

The Code, Explained

Width resolves immediately, using only information already available:

block_layout.py
content_width = _resolve_size(
    width_spec, containing_block.width - margin.horizontal,
    padding.horizontal, border.horizontal, box_sizing,
)

Height is different — notice it's computed AFTER the entire children loop, using a value (`cursor_y`) that loop just finished producing:

block_layout.py
for child in node.children:
    ...
    child_box = layout_block(child, child_cb, styles)
    cursor_y += child_box.margin_box_height

if height_spec == "auto":
    content_height = cursor_y - content_y   # only correct AFTER the loop

Nothing special makes this ordering happen — it's just where the lines of code physically sit. That's the whole trick: recursion plus "read the loop result after the loop" is sufficient to get top-down position and bottom-up sizing both correct, in one function, without two separate passes over the tree.

Limits / What You Cannot Do Yet

Can't do yet

  • Lay out inline content or text at all — completely skipped, not even attempted (Module 12)
  • Anything a user-agent stylesheet would normally give you for free — every display: block must be stated in the test CSS
  • Percentage widths/heights, floats, or positioned (absolute/fixed) elements

Can do now

  • Correctly position a recursively nested tree of block boxes
  • Correctly resolve width: auto against a real containing block
  • Correctly resolve height: auto from real children, computed bottom-up

Brain Exercise

🧠 Think before you reveal

This module's own first test run failed two checks that turned out to be wrong TEST assertions, not layout bugs. One compared two sibling nodes' content-box y-coordinates to check how far apart they were vertically. Why is that the wrong pair of numbers to compare for that question, even though the layout itself was already correct?

Reveal the answer

Because each node's content-box y already has that SAME node's own margin-top + border-top + padding-top baked into it — and different nodes can have different values for those. #a has zero border/padding, so its content y equals its border-box y. #b has a 2px border and 5px padding, so its content y sits 7px BELOW its own border-box y. Comparing `a.content_y` to `b.content_y` doesn't measure "how far the layout cursor moved between placing these two boxes" — it measures that PLUS an extra 7px that belongs to `#b`'s own box structure, not to the gap between the two boxes. The correct comparison uses each node's BORDER-box y (the actual outer edge the cursor is tracking), which is exactly the fix applied here. This is a good general lesson: when verifying geometry, always be explicit about WHICH edge of a box you're comparing — content, padding, border, and margin edges are all different numbers, and mixing them across two different nodes produces answers that look plausible but are quietly wrong.

There Are No Dumb Questions

Why does auto-width never need to look at children, but auto-height does?
Because that's literally how the CSS spec defines block-level normal flow: width is resolved top-down from the containing block (a box doesn't get to be wider than the space it was given), while height falls out bottom-up from content unless explicitly overridden. It's an intentional asymmetry in the spec, not something this module invented — real browsers have exactly the same lopsided dependency.
Could this same recursive-function trick handle inline layout too, or is Module 12 doing something fundamentally different?
Fundamentally different, and that's why it's a separate module rather than an extension of this one. Block children stack strictly vertically, one per "row" — the cursor only ever needs to track a single Y value. Inline content has to track a horizontal cursor too, decide when a word doesn't fit and needs to wrap to a new line, and handle several inline elements sharing one line's height. That's a different algorithm shape, not just "the same thing with more properties."
The demo hardcodes a viewport width of 800. Where would that number really come from?
From the actual rendering surface — Module 15's Tkinter canvas will have a real pixel width, and that's what a real browser's viewport width is: the size of the window you're looking at. This module doesn't have a canvas yet, so 800 is a stand-in, named explicitly as one rather than presented as if it came from somewhere meaningful.
