The Big Analogy

🍽️ The Restaurant, continued

A junior line cook is never given a key to the walk-in freezer or the liquor cabinet. If they need something from either, they ask a manager, who fetches it for them. That's the polite version of the system — and it works great, right up until you ask: what if the "junior line cook" is actually an intruder who snuck into the kitchen wearing a stolen uniform? Politely asking a manager for the key does nothing to stop someone who was never going to ask in the first place — they'll just walk to the freezer themselves. The thing that ACTUALLY stops them isn't the "please ask first" custom — it's the freezer door being physically locked, with a lock the manager controls and the intruder's stolen uniform doesn't open. This module builds the "please ask first" system in full, working detail — and then shows, honestly, that without the physical lock, it stops absolutely nobody who wasn't already going to cooperate.

What Happens, Step by Step

  1. A broker process (trusted, holds real file access) launches a renderer process as a genuinely separate OS process, connected only by two pipes (stdin/stdout).
  2. For a COOPERATIVE request: the renderer sends a JSON request over the pipe and waits — it has no file-opening code in this path at all.
  3. The broker checks the request against a policy (is the resolved, absolute path inside the one allowed directory?).
  4. If allowed, the broker itself opens and reads the real file, sending the content back. If denied, it sends back an error — and its own access log proves it never opened the file at all.
  5. For a MALICIOUS request: the renderer ignores the entire protocol and calls open() directly, itself — simulating a compromised renderer that no longer follows any rules.
  6. That direct read succeeds — because nothing in this module's Python-only toolchain stops an OS process from making its own system calls. This is the module's actual point.

A Map of the Two Paths

COOPERATIVE PATH (the renderer follows the rules): renderer broker (real file access) │ {"request":"read_file", │ │ "path": "..."} │ │ ───────────────────────────────────────▶│ │ │ check Policy │ │ ALLOWED -> open() for real │ │ DENIED -> never opens it │ {"ok": true/false, ...} │ │ ◀───────────────────────────────────────│ ▼ renderer only ever learns what the broker chooses to tell it MALICIOUS PATH (the renderer ignores the rules): renderer broker │ open(secret_path) <-- DIRECTLY, no request sent at all │ SUCCEEDS — the OS has no idea a "broker" or "policy" exists ▼ the broker's policy is 100% BYPASSED, not defeated — just never consulted

the top path is a real, working protocol; the bottom path shows exactly what that protocol does and doesn't protect against

The Code, Explained

The broker's file access is the ONLY real file-reading code in the cooperative path — this single fact is what makes a denial provable, not just claimed:

sandboxing.py
if self.policy.permits_read(request["path"]):
    self.opened_paths_log.append(request["path"])
    with open(request["path"], "r") as f:
        data = f.read()
    self._send({"ok": True, "data": data})
else:
    self._send({"ok": False, "error": "policy denied: ..."})

The `opened_paths_log` isn't decoration — it's what lets this module's checks confirm the secret file's path never appears there after a denial, rather than just trusting the error message.

And the line that this entire module exists to make visible — the renderer, given a chance to misbehave, simply does:

renderer_worker.py
elif action == "malicious_read":
    # Ignore the protocol. Just open the file ourselves.
    with open(path, "r") as f:
        data = f.read()
    send({"result": "malicious_read", "ok": True, "data": data})

Nothing about `subprocess.Popen`, the JSON protocol, or the `Policy` class prevents this method from being called and succeeding. The OS lets this process open this file, full stop — the broker was never even in the loop.

Limits / What You Cannot Do Yet

Can't do yet

  • Actually PREVENT a malicious/compromised renderer from bypassing the broker — this module proves it CANNOT, on purpose
  • Any real OS-level syscall filtering (seccomp-bpf, restricted tokens, sandbox profiles) — named in detail below, none implemented
  • Network-request or clipboard/device mediation — only file reads are modeled, as the clearest minimal example

Can do now

  • Build a real, working broker/target process architecture matching real browsers' structural pattern
  • Prove a policy-based denial is real (via an access log), not just a returned error string
  • Name precisely — not vaguely — which real OS primitive would close the gap this module deliberately leaves open

⚠ Getting a blank or broken result?
  • The subprocess hangs: the broker/renderer protocol is strictly turn-based (broker sends, renderer sends back, broker reads) — if either side sends two lines in a row without the other reading in between, both processes will block waiting on each other forever. Check the exact send/receive order in both files matches.
  • TEST 3 unexpectedly gets DENIED: double check `renderer_worker.py`'s `malicious_read` branch really does call `open()` directly and isn't accidentally routed through the broker request/reply protocol.

Brain Exercise

🧠 Think before you reveal

Real Chromium's actual sandboxed renderer process CANNOT simply `open()` an arbitrary file the way this module's malicious renderer can — even though Chromium's renderer is also, underneath, an ordinary OS process running ordinary code. Given everything built in this module, what SPECIFIC extra thing would need to exist for `malicious_read` to actually fail here the way it does in a real browser?

Reveal the answer

The operating system's KERNEL would need to be told, from OUTSIDE the renderer process, to reject that specific `open()` syscall before it executes — regardless of what the process's own code (compromised or not) asks for. On Linux, this is a seccomp-bpf filter installed on the process (typically right after it starts, before any untrusted code runs) that the kernel enforces on every subsequent syscall that process ever makes — no amount of code running INSIDE that process, however malicious, can lift a filter enforced from outside it by the kernel. This course's `renderer_worker.py` has no such filter installed — it's an ordinary, unrestricted Python process, which is precisely why its `open()` call in `malicious_read` succeeds exactly like any normal Python script's would. The broker/target PROCESS SPLIT this module built is a real, necessary piece of the real architecture — but it's the kernel-level filter, not the process split alone, that provides the actual enforcement.

There Are No Dumb Questions

If this module "doesn't actually work" as a real sandbox, why build it at all?
Because the ARCHITECTURE — a trusted broker process mediating requests from an untrusted renderer over a narrow, explicit channel — is genuinely how real browsers are structured, and understanding that structure is real, transferable knowledge. What this module is careful never to claim is that the architecture alone, without OS enforcement underneath it, constitutes real security. Building the honest, working version of the "asking politely" layer, and then honestly demonstrating its limit, teaches the actual shape of the problem better than either skipping the demo or overstating what it proves.
Would running the broker as a different OS USER than the renderer fix this?
It would help — real sandboxes do sometimes use reduced-privilege OS users/tokens as one layer — but it's not sufficient on its own either. A renderer running as a low-privilege user can typically still read any file that user account has ordinary read access to (which, for a normal desktop user, is often "most of their own files"), so a determined malicious renderer could still read plenty of sensitive data without ever needing the broker. Real sandboxes combine reduced privileges WITH syscall-level filtering (seccomp-bpf, etc.) specifically because privilege reduction alone leaves this exact gap.
Where does Module 23's same-origin policy fit relative to this module's sandbox?
They're different layers protecting against different threats. Same-origin policy (Module 23) is a JS-engine-level rule about what a NORMAL, non-compromised script running in a tab is allowed to do — it assumes the renderer process itself is behaving correctly and just restricts what the SCRIPT inside it can request. Sandboxing (this module) assumes the opposite worst case — that the renderer process ITSELF has been compromised (its code is no longer trustworthy at all, same-origin checks included, since they'd be running inside the very process an attacker now controls) — and asks what stops it from reaching the rest of the system regardless. Real browsers need both: same-origin policy for well-behaved scripts, OS-level sandboxing as the backstop for when a renderer stops being well-behaved entirely.
