URL Encoding & Decoding

Before any HTML is involved, a URL can already be tricked into carrying structure its author never intended — if a value crossing into it isn't encoded first.

📄 Companion doc: DECISIONS.md · Source: url_encoding.py

Prerequisites

Module 2: URL Parser Bytes & Text Encoding

The Big Analogy

🍽️ The Restaurant, continued

An order form has structured fields separated by commas: "table, dish, special-instructions." If a guest's special instructions happen to literally contain the word "table" followed by a comma and a fake dish name, and the kitchen just pastes that text into the form without any escaping, the form now LOOKS like it has extra, legitimate-seeming fields it never actually had. Percent-encoding is the restaurant putting quotes around free-text fields and escaping any comma found inside them — so "table, extra-free-dessert" stays one instruction, not two fields pretending to be part of the form's real structure.

What Happens, Step by Step

  1. Take a value that's about to be inserted into a URL (a query parameter's value, a path segment).
  2. Convert it to its raw UTF-8 bytes — encoding has to work on bytes, not characters, to handle non-ASCII text correctly.
  3. For every byte that ISN'T one of URL's safe "unreserved" characters (letters, digits, - . _ ~), replace it with % plus its two-digit hex value.
  4. Splice the now-encoded value into the URL. Any character that used to mean "start a new parameter" or "end the path" is now just %XX text — inert, structurally meaningless.
  5. On the way back out, reverse the process: collect raw bytes (decoding each %XX, passing other characters through as their own UTF-8 bytes), then decode the whole byte sequence as UTF-8 once, at the end.

A Map of the Attack and the Fix

user input: cats&admin=true WITHOUT encoding: URL: https://site.example/search?q=cats&admin=true Module 2 parses query as: "q=cats&admin=true" ^^^^^^^^^^ looks like a REAL second parameter! WITH encode_uri_component() first: URL: https://site.example/search?q=cats%26admin%3Dtrue Module 2 parses query as: "q=cats%26admin%3Dtrue" \_______________/ ONE value, '&' and '=' are now inert text percent_decode("cats%26admin%3Dtrue") -> "cats&admin=true" (unchanged, whole)

encoding doesn't hide or destroy the attacker's text — it strips its ability to be reinterpreted as syntax

The Code, Explained

The whole encoder is a per-byte decision, one line:

url_encoding.py
for byte in s.encode("utf-8"):
    ch = chr(byte)
    if ch in UNRESERVED or ch in safe:
        out.append(ch)
    else:
        out.append(f"%{byte:02X}")

Note it iterates s.encode("utf-8") — bytes — not s itself. That's what keeps non-ASCII text correct: a character like é is two bytes, and each byte gets its own independent encoding decision.

The security-relevant check reuses Module 2 directly, rather than just asserting the fix works:

url_encoding.py
parsed_unsafe = parse_url(unsafe_url)   # Module 2, unmodified
print(f"'admin=true' in parsed_unsafe.query.split('&')")  # True — the exploit is REAL

Limits / What You Cannot Do Yet

Can't do yet

  • Prevent injection into HTML body content — that's a completely different context with different rules (Module 27)
  • Match real JavaScript's `encodeURIComponent` byte-for-byte — this module's version is slightly more conservative (see DECISIONS.md)

Can do now

  • Correctly, losslessly round-trip encode/decode any text, including non-ASCII
  • Prevent a real, reproduced query-string injection attack
  • Correctly choose between "encode one value" and "encode a whole URI" — using the right safe-character set for each

Brain Exercise

🧠 Think before you reveal

If a developer used `encode_uri` (not `encode_uri_component`) on the user's search text in Case 2 — the function meant for whole URIs, not single values — would the injection still be prevented?

Reveal the answer

No — and this is exactly why using the WRONG one of these two functions is a real, common vulnerability pattern, not just a stylistic mismatch. `encode_uri`'s safe set explicitly includes `&` and `=` (because those characters are supposed to survive intact when you're encoding an already-complete URI). Running the user's `"cats&admin=true"` through `encode_uri` would leave the `&` and `=` completely untouched, producing the exact same vulnerable URL as not encoding at all. The safety here doesn't come from "encoding was applied" in the abstract — it comes from applying the RIGHT encoding function for what's actually being encoded: a single untrusted VALUE, not a trusted, pre-structured URI.

There Are No Dumb Questions

Is this the same kind of bug as XSS?
It's the same FAMILY of bug — untrusted data crossing into a context where certain characters mean something structural, without being neutralized first — but this specific case (query-string injection) doesn't run any script; it just smuggles extra parameters. The pattern generalizes directly to Module 27, where the "structural characters" are `<` and `>`, and the consequence becomes actual code execution.
Why does `encode_uri_component` encode MORE than real JavaScript's version?
A deliberate, named choice (DECISIONS.md) — real `encodeURIComponent` leaves a handful of characters (`! * ' ( )`) unescaped for historical reasons tied to an older URI spec. This module sticks strictly to RFC 3986's actual unreserved set, which means it over-encodes those few characters relative to real JS — strictly safer, never less safe, and simpler to reason about without needing to memorize a historical exception list.
Could you encode the ENTIRE URL, including the `https://`, the host, and the `?`, all with `encode_uri_component`?
You could run the function on that whole string, but the result would no longer be a valid URL at all — `encode_uri_component` would escape the `:`, `/`, and `?` characters that GIVE the URL its structure, turning `https://site.example/search?q=x` into meaningless percent-encoded text. This is exactly the mistake `encode_uri` exists to avoid — always match the function to whether you're encoding a whole structured URI or one untrusted piece going into it.

What's Next

The same core idea — encode untrusted data before it crosses into a context with its own syntax — moves next to the context where the stakes get much higher: HTML body content, where the "structural characters" are the ones that turn plain text into a running <script> tag.
