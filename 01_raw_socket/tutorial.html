The Big Analogy

🍽️ The Restaurant, continued

This module is the runner's entire job, and nothing else. The runner doesn't know how to cook, doesn't know the menu, doesn't even know what a "dish" is — their whole skill is: walk to the correct warehouse address, knock, hand over a slip of paper, wait, and carry back whatever crate comes out, sealed, unopened. Whether the crate contains a full HTML page or a JSON error, the runner's job is identical: open the door, exchange something, close the door.

That's exactly what `raw_socket.py` does — it doesn't know what HTTP is (that's Module 3), it just proves the door can be opened and something real can be carried through it.

What Happens, Step by Step

  1. socket.socket(AF_INET, SOCK_STREAM) creates an unconnected socket object — a promise of a connection, not a connection yet.
  2. sock.connect((host, port)) triggers DNS resolution (host → IP, done by the OS) and then the TCP three-way handshake (SYN / SYN-ACK / ACK, also done by the OS) — after this line returns, a real, live, ordered byte pipe exists between your machine and the server.
  3. send_all() pushes our hand-built request bytes down that pipe, looping if the OS can't send everything in one call.
  4. recv_all() reads back whatever the server sends, in a loop, until the server closes its end (signaled by recv() returning empty bytes).
  5. sock.close() releases the connection. The raw bytes we received are now just a Python bytes object — no different from any other data in memory.

A Map of the Connection

YOUR MACHINE example.com (client) (server, port 80) socket.socket() ---- unconnected ---- .connect(("example.com", 80)) | |-- DNS: "example.com" -> 23.x.x.x (OS resolver, not us) | |== TCP handshake: SYN -> <- SYN-ACK -> ACK == (OS kernel, not us) | v local 10.2.0.2:57937 <===== TCP byte stream =====> 23.x.x.x:80 | |-- send_all(b"GET / HTTP/1.0\r\n...") --> | | <-- recv_all() collects bytes until peer closes -- | sock.close() (server closes its end)

everything above the byte-stream line is the OS's job; everything we wrote is the two send/recv loops

The Code, Explained

The connection itself is three lines — the two socket "constants" are where the real decisions live:

raw_socket.py
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.settimeout(timeout)
sock.connect((host, port))

AF_INET and SOCK_STREAM aren't arbitrary names — they're the two facts a socket needs before it can exist: what kind of address (IPv4) and what kind of transport (TCP, a reliable ordered stream — required because HTTP is specified to assume one). See DECISIONS.md for why each is categorized as an external contract, not a free choice.

The receiving loop is the part most tutorials skip past — and the part most worth sitting with:

raw_socket.py
def recv_all(sock, chunk_size=4096):
    chunks = []
    while True:
        chunk = sock.recv(chunk_size)
        if not chunk:          # empty bytes = the peer closed the connection
            break
        chunks.append(chunk)
    return b"".join(chunks)

recv(4096) asks for up to 4096 bytes but is free to hand back fewer — a slow network might deliver 200 bytes at a time. The loop keeps calling recv() until it gets back b"", which the socket API reserves specifically to mean "the other side hung up," never "nothing to read yet." That distinction is the entire reason this is a loop and not a single call.

⚠ Getting a blank or broken result?
  • Hangs, then times out after 5s: something between you and port 80 is blocking outbound traffic (corporate firewall, restricted sandbox). Try a different network.
  • ConnectionRefusedError: nothing is listening on that host:port — double check you didn't typo the port.
  • Garbled characters in the console (e.g. a stray �) but the program still finishes: that's your terminal's own encoding (commonly cp1252 on Windows) failing to display a Unicode character in this tutorial's own text, not a bug in the socket code — the actual received bytes are unaffected.
  • socket.gaierror: DNS resolution failed — the hostname itself couldn't be looked up. Confirm you can reach the internet at all.

Brain Exercise

🧠 Think before you reveal

The demo works because the request includes Connection: close, which makes the server hang up after one response. What would happen — concretely, in terms of what line of code gets stuck — if you removed that header and the server honored HTTP/1.1's default of keeping the connection open?

Reveal the answer

recv_all()'s while True loop would never see recv() return b"", because the server never closes its end — it's sitting there, connection open, waiting to see if you'll send another request on the same socket. The loop would keep calling recv(), which would block waiting for more data that isn't coming, until sock.settimeout(5.0) finally fires a socket.timeout exception. This is exactly why a real HTTP client can't rely on "read until closed" — it has to read the Content-Length header (or handle chunked encoding) and stop reading at the byte count the server told it to expect. Module 3 builds exactly that.

There Are No Dumb Questions

Why didn't we just use Python's requests library — isn't that what everyone actually uses?
In real code, absolutely — requests is well-tested and handles dozens of edge cases this course skips. But the entire point of this course is to see what requests is doing on your behalf. Every socket call in this module is a line of code that exists, unseen, somewhere inside every HTTP library you've ever used.
Is the local port number (57937 in the sample output) something the server cares about?
No — it's an "ephemeral port," assigned by your OS from a pool of temporary ports specifically so the server has a return address to send responses to. You didn't choose it, and a different run will get a different one. The server only cares about the port it's listening on (80, in this case).
Could recv_all() ever return the wrong bytes, out of order?
No — this is precisely the guarantee TCP (SOCK_STREAM) provides: bytes arrive in the exact order they were sent, with none missing or duplicated, or the connection errors out entirely. That guarantee is why HTTP is layered on TCP and not UDP. See the client-server prereq.
What actually happens during "the TCP handshake" mentioned in the diagram?
Three packets, invisible to our code: your machine sends a SYN ("I'd like to connect"), the server replies SYN-ACK ("acknowledged, I'd like to connect too"), your machine replies ACK ("acknowledged"). Only after all three does sock.connect() return. This is entirely handled by the OS kernel's TCP implementation — it's the canonical example of what this course treats as "hardware."
