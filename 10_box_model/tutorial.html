The Box Model

Every element on every webpage is a rectangle, wrapped in three more rectangles. "width: 300px" doesn't always mean what it looks like it means.

The Big Analogy

🍽️ The Restaurant, continued

A plated dish has the food itself (content), the rim of the plate that keeps sauce from running (padding), the plate's own physical edge (border), and the empty tablecloth space kept clear around it so plates don't touch (margin). Here's the twist that trips people up in real kitchens too: when someone says "this plate is 12 inches," do they mean the food area alone, or the whole plate including its rim? Get that wrong and you'll cut a hole in the tablecloth layout that's the wrong size — which is exactly what box-sizing is actually deciding.

What Happens, Step by Step

  1. Read box-sizing first — content-box (the default) or border-box — because it decides what the width/height numbers even mean.
  2. Read the four padding values, the border width, and the four margin values.
  3. If width is auto, stop — this module deliberately doesn't guess; that's Module 11's job, since it needs to know the containing block.
  4. Otherwise, if box-sizing is border-box, SUBTRACT padding and border from the declared width to get the actual content width. If it's content-box, the declared width IS the content width, unchanged.
  5. Build the box outward, one layer at a time: content → padding box (content + padding) → border box (padding box + border) → margin box (border box + margin).

same four numbers (width, padding, border, margin) — box-sizing decides which rectangle "width" is naming

The Code, Explained

The single line that IS this module's point:

box_model.py
if box_sizing == "border-box":
    return max(0.0, spec - pad - bor)
return spec   # content-box: the number IS the content size

Same inputs (spec, pad, bor), two completely different formulas, selected by one property. This is why `box_sizing` is read at the very top of `compute_box()`, before any content-size arithmetic happens at all — everything downstream depends on which formula got selected here.

And the box expands outward, layer by layer, each one only knowing about the layer directly inside it:

box_model.py
@property
def border_box_width(self) -> float:
    return self.padding_box_width + self.border.horizontal

Limits / What You Cannot Do Yet

Can't do yet

  • Resolve width: auto to a real size — needs the containing block (Module 11)
  • Give any box a position on the page — this module only computes SIZE
  • Independent border widths per side (uniform on all four here)
  • Percentage, em, or other relative units

Can do now

  • Correctly compute content/padding/border/margin box sizes for explicit widths
  • Correctly handle box-sizing: border-box vs. the content-box default
  • Prove, with real arithmetic, exactly how those two modes diverge from identical input

⚠ Getting a blank or broken result?
  • border-box's border_box_width isn't exactly the declared width: check the subtraction happens BEFORE building the box outward, not after — content width must already be the shrunk value going in.
  • Negative content width on tiny boxes with large padding: max(0.0, ...) in `resolve()` clamps this — real browsers do the same rather than allowing negative content areas.

Brain Exercise

🧠 Think before you reveal

A designer hands you a mockup where every box is specified by its OUTER edge — "this button is 44x44px including its border," full stop, regardless of how much border or padding it has. Which box-sizing value makes implementing that mockup trivial, and which one would force you to do subtraction math by hand for every single element?

Reveal the answer

border-box makes it trivial — you write width: 44px and the border box IS 44px, regardless of how much padding or border you also add, because `compute_box()` does the subtraction for you. With `content-box` (the default), you'd have to manually compute `44 - padding*2 - border*2` and put THAT number in `width` — and if a designer later changes the padding, every one of those hand-computed widths silently becomes wrong. This is exactly why many real-world CSS resets set `box-sizing: border-box` globally as one of the first rules in a stylesheet — it makes "the number you type is the number you get on screen" true, matching how most visual design tools already think about sizing.

There Are No Dumb Questions

Why does `width: auto` stop at exactly 0.0 instead of trying to compute something more sensible?
Because "something more sensible" genuinely requires information this module doesn't have — the size of the containing block, which only exists once you're walking the actual layout tree. Guessing here would mean this module either silently produces wrong numbers or duplicates logic Module 11 needs to own anyway. Stopping at a clearly-flagged placeholder value, tested explicitly, is more honest than a plausible-looking wrong answer.
Is treating border-width as one uniform value a big limitation?
For this course's own test pages, no — but it's real, and DECISIONS.md names it rather than hiding it. If a later module needed independent border widths per side, `_edges()` already has the exact right shape (it's what padding and margin already use) — border would just need to stop using the `uniform_key` shortcut.
Why compute `border_box_width` as `padding_box_width + border.horizontal` instead of directly from `content_width`?
Because that's not how the box model is actually defined — each layer is defined in terms of the layer immediately inside it, never by skipping straight to content. Writing the code the same way keeps the code's structure a direct, checkable translation of the box model diagram, rather than an equivalent-but-differently-organized formula that happens to produce the same number.

What's Next

Every box now has a correct SIZE. None of them have a POSITION yet — box_model.py never once mentions x or y. Module 11 walks the actual DOM tree and, box by box, computes where each one sits on the page — including finally resolving the width: auto case this module deliberately left alone.
