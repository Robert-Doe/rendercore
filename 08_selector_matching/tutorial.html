The Big Analogy

🍽️ The Restaurant, continued

The style guide (Module 7) says "for anything tagged 'soup' that's on a table inside the 'formal' section, use the silver spoon." Now a specific dish is in front of you: is it soup? Is the table it's on actually inside the formal section, or just near it? You don't check "is this table literally touching the formal section's rope" — you check "if I trace outward from this table through every enclosing area, do I ever cross into 'formal'?" That outward trace, one enclosing area at a time, is exactly how a descendant combinator gets checked here.

What Happens, Step by Step

  1. For a given node and a given selector, check the rightmost compound selector against the node itself first — type, id, and classes must ALL match (an AND, never an OR).
  2. If that fails, the whole selector fails immediately — no need to look at ancestors at all.
  3. If it succeeds and there are more compounds to the left, walk up from the node's parent, ancestor by ancestor, looking for one that matches the next compound to the left.
  4. Repeat leftward until every compound has matched some ancestor (success) or an ancestor walk runs out before finding a match (failure).
  5. A rule matches a node if any of its comma-separated selectors match — .card, .panel applies if either matches.
  6. Collect every rule in the stylesheet that matches, keeping the stylesheet's original order — Module 9 needs that order.

The Code, Explained

The whole algorithm is two small functions working together:

selector_matching.py
def matches_selector(node, selector):
    parts = selector.parts
    if not matches_simple(node, parts[-1]):    # rightmost, against the node itself
        return False
    current = node
    for part in reversed(parts[:-1]):           # walk leftward
        current = _find_matching_ancestor(current, part)
        if current is None:
            return False
    return True

Notice this never looks at children — only the node itself and its ancestors. That asymmetry is deliberate and matches how descendant combinators are actually defined: they describe a relationship going up the tree from the element being styled, never down.

Limits / What You Cannot Do Yet

Can't do yet

  • Decide which of several matching rules WINS on a conflicting property (Module 9)
  • Match child/sibling combinators (Module 7 doesn't parse them, so this module never sees them)
  • Match pseudo-classes like :hover (not parsed by Module 7)

Can do now

  • Correctly match compound selectors (type + class + id, ANDed)
  • Correctly match descendant-combinator chains by walking real ancestors
  • Correctly NOT match a selector against a node's descendants when the selector targets the node's ancestor, not the node itself

⚠ Getting a blank or broken result?
  • Every node seems to match every rule: check matches_simple's early returns — an accidentally inverted condition there (returning True instead of False on mismatch) would make everything match.
  • Descendant selectors never match anything: confirm _find_matching_ancestor starts from node.parent, not node itself — starting from the node would let a selector match itself twice against the same compound.

Brain Exercise

🧠 Think before you reveal

Why is it safe for _find_matching_ancestor to stop at the FIRST matching ancestor it finds, without checking whether a match further up would also work and picking a "better" one? What specific property of this course's selector support (established back in Module 7) makes that safe?

Reveal the answer

Because Module 7 only parses the descendant combinator, every ancestor of a given node lies on one single, non-branching chain up to the document root. Any ancestor further up that chain which matches an even-earlier compound selector is, by simple transitivity of "is an ancestor of," also an ancestor of every closer-matching node below it on that same chain — so picking the closest match can never rule out a valid selector that a farther match would have completed. This stops being true the moment child (>) or sibling (+, ~) combinators enter the picture, because those introduce real branching choices where the nearest match genuinely might be a dead end — which is exactly why real browser engines need backtracking (or smarter indexed matching) once those combinators are supported, and why DECISIONS.md calls this out as a provable consequence of a scope limitation, not a coincidence.

There Are No Dumb Questions

Why does matching start from the node and work UPWARD toward the root, instead of starting at the root and searching DOWNWARD for a match?
Performance, primarily — and it compounds. A browser calls this matching logic for every rule against every node on the page. Starting at the specific node and checking the cheapest, most identifying thing first (does this element itself match the last compound?) lets almost every non-matching rule get rejected in one check, before any tree-walking happens at all. Starting from the root and searching down would mean exploring huge swaths of the tree for rules that were never going to match this node anyway.
If .card doesn't match the <p> inside a div class="card", how would you write a selector that DOES reach that paragraph?
.card p — a two-part descendant selector, exactly like nav a.active. A bare .card is a one-part selector; it only ever describes the element that itself carries the class, never anything nested inside it. This distinction — one compound vs. a chain of compounds — is the entire reason `.card` and `.card p` produce different matches in this module's test.
Could a node match the same rule through two different selectors in its comma group at once?
Yes, and `matches_rule`'s `any(...)` handles that correctly — it only needs one selector in the group to match; it doesn't need to know or care if more than one did. Module 9 also only cares that the rule matched at all, not how many of its selectors did.

What's Next

Every node in this module's demo matched more than one rule at once — the active link matched three. Real pages have this constantly: many rules apply to the same element, and they don't always agree. Module 9 builds the algorithm that picks exactly one winning value per property when that happens.
