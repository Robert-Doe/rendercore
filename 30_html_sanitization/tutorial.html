HTML Sanitization

Modules 27-29 encoded EVERYTHING away. This module has to let some of it through — and decide, precisely, how much.

📄 Companion doc: DECISIONS.md · Source: html_sanitization.py

Prerequisites

The Big Analogy

🍽️ The Restaurant, continued

A restaurant lets guests write a short note on their own comment card — maybe underline a word, maybe circle something — using a small, approved set of markers on the card itself. The staff doesn't ban markers entirely (that would make comment cards useless); they don't trust every possible mark a guest could make either. They check: is this mark one of the ones we specifically allow (underline, circle, a small star)? Anything else — a mark we've never seen before, a mark shaped like an official kitchen stamp — gets scraped off, while the guest's actual WORDS stay exactly where they were.

What Happens, Step by Step

  1. Parse the untrusted HTML into a real DOM tree (Module 6) — the same tree-building logic used everywhere else in this course.
  2. Walk it bottom-up: a node's own children get sanitized FIRST, before deciding the node's own fate.
  3. If a node's tag is genuinely dangerous (script, style, iframe, ...), drop it and everything inside it — content included.
  4. If a node's tag isn't on the explicit allowlist (but isn't dangerous either), UNWRAP it — discard just the tag, keep its already-sanitized children in its place.
  5. For everything that survives as a real tag, filter its attributes down to an allowlist per tag — and separately, check any surviving href/src VALUE for a dangerous URL scheme, even though the attribute NAME itself was allowed.

A Map of One Sanitization Pass

INPUT: <p>Hello <b>world</b></p> <script>alert(document.cookie)</script> <a href="javascript:alert(1)">click here</a> <img src="x.png" onerror="alert(1)"> <fancybox>weird custom tag</fancybox> <div onclick="alert(1)">Click me</div> script -> DANGEROUS_TAGS -> DROPPED, subtree and all a href="javascript:..." -> tag ALLOWED, but href SCHEME dangerous -> href attribute dropped, <a> kept, text kept img onerror=... -> tag ALLOWED, onerror NOT in allowlist -> onerror dropped, src (safe scheme) kept fancybox -> not dangerous, not allowed -> UNWRAPPED -> tag gone, "weird custom tag" text SURVIVES div onclick=... -> tag ALLOWED, onclick NOT in allowlist -> onclick dropped, div + "Click me" text kept OUTPUT (tags): p, b, a, img, div <- script and fancybox both gone, for two DIFFERENT reasons

every removal has a specific, checkable reason — never "delete everything to be safe"

The Code, Explained

The unwrap-vs-drop distinction is the single `if` that makes this module's whole design point visible:

html_sanitization.py
if child.tag in DANGEROUS_TAGS:
    continue                                   # drop tag AND content
child.children = sanitize_children(child.children)   # recurse first
if child.tag in ALLOWED_TAGS:
    result.append(child)                        # keep the tag
else:
    result.extend(child.children)                # UNWRAP: keep content, drop the tag

And the URL-value check that runs independently of the attribute-name allowlist:

html_sanitization.py
if name in URL_ATTRS and is_dangerous_url_scheme(value):
    continue   # allowed ATTRIBUTE NAME, dangerous VALUE — dropped anyway

Limits / What You Cannot Do Yet

Can't do yet

  • Tag-specific attribute nuance beyond a flat per-tag allowlist (e.g. allowing class only for specific known-safe values)
  • CSS sanitization — a style attribute's VALUE isn't checked at all (and style the TAG is dropped outright)
  • Preserve HTML comments — dropped unconditionally (DECISIONS.md)

Can do now

  • Remove genuinely dangerous tags, subtree and all
  • Preserve real, safe structure and text through unwrapping rather than destroying everything unrecognized
  • Catch a dangerous URL VALUE even when the attribute NAME carrying it is entirely legitimate

⚠ Getting a blank or broken result?
  • Script content survives as stray text: confirm `DANGEROUS_TAGS` handling uses `continue` BEFORE recursing into the child's children — recursing first would sanitize and preserve the script's text content as if it were ordinary text.
  • Every unknown tag's content disappears instead of unwrapping: check the `else` branch extends the result list with `child.children`, not skips the child entirely.

Brain Exercise

🧠 Think before you reveal

Why does `_sanitize_attrs` check the URL scheme SEPARATELY from the name-based allowlist, instead of just adding `href="javascript:*"` as a special denylist pattern the allowlist also consults?

Reveal the answer

Because the name-allowlist and the value-scheme-check are answering two genuinely different questions, and conflating them back into one combined allowlist would reintroduce exactly the denylist fragility this module's whole design tries to avoid. "Is `href` a permitted attribute NAME for ``?" is a simple, closed, easy-to-get-right yes/no question. "Is this particular URL VALUE safe?" is open-ended — Module 28 already had to account for a real bypass technique (a hidden tab character) that a naive check missed, and future new bypass techniques may still be discovered. Keeping the two checks separate means the URL-scheme logic can be improved, extended, or reused (exactly as this module reuses Module 28's function unmodified) without touching the attribute-name allowlist at all, and vice versa.

There Are No Dumb Questions

Why is this module so much more complex than Modules 27-29?
Because it's solving a genuinely harder problem. Modules 27-29 all had the luxury of "neutralize everything, no exceptions" — there was no requirement to preserve any structure. Sanitization exists specifically for cases where SOME real HTML has to survive (a comment system that allows bold text and links), which means every single tag and attribute needs an explicit, considered decision instead of one blanket rule.
Is dropping HTML comments unconditionally overly cautious?
For most ordinary content, probably somewhat — the vast majority of user-submitted comments containing an HTML comment are entirely harmless. But comments have a real, documented history of being involved in parser-differential attacks (different parsers historically disagreeing about where a comment ends), and the actual VALUE of preserving user-submitted HTML comments in typical rich-text content is close to zero. This module makes the conservative call explicitly, rather than leaving it as an unexamined default.
Could this sanitizer be bypassed the way Module 28's naive scheme check was?
Its URL-scheme check specifically reuses Module 28's ALREADY-FIXED version (`is_dangerous_url_scheme`, not the naive one), so the tab-hiding bypass Module 28 demonstrated is already closed here. That said, this module's own allowlists are deliberately small and illustrative, not exhaustively researched against every historical HTML sanitizer bypass technique — a real production sanitizer (like DOMPurify) encodes years of accumulated, hard-won knowledge about edge cases this module doesn't attempt to replicate.
