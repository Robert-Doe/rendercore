Prerequisites

Processes vs. Threads

The Big Analogy

🍽️ The Restaurant, continued

Each table's food truck (Module 0's analogy for a tab) is a physically separate vehicle, not a shared kitchen station with a piece of tape on the floor marking "table 5's area." If truck 5 catches fire, truck 9 keeps cooking — not because anyone told the fire to stay put, but because there's an actual gap of open air between two separate vehicles that fire simply cannot cross on its own. That's the entire difference this module is about: a rule that says "don't cross this line" versus a line that's a physical wall.

What Happens, Step by Step

  1. The main "chrome" process starts three worker processes — real, separate OS processes, one per tab — via multiprocessing.Process, not threads.
  2. Each worker reports its OWN process ID, observed from inside itself — proof, not assertion, that these are genuinely different processes.
  3. All three tabs are pinged. Two respond normally. One is configured to raise a real, unhandled exception instead — a simulated renderer crash.
  4. That process's exit code is checked: non-zero confirms it genuinely crashed, not that it quietly finished.
  5. The two surviving tabs are pinged AGAIN, after the crash — and respond with real answers from the exact same process IDs as before, proving they were never affected at all.

A Map of the Four Processes

chrome (main, pid 12724) ├── tab_a (pid 21564) ── ping ──▶ "pong" ├── tab_b (pid 7544) ── ping ──▶ RuntimeError, unhandled │ process exits with code 1 └── tab_c (pid 23760) ── ping ──▶ "pong" AFTER tab_b's crash: chrome (pid 12724, unchanged, never stopped running) ├── tab_a (pid 21564) ── ping AGAIN ──▶ "pong" (same pid, fully alive) └── tab_c (pid 23760) ── ping AGAIN ──▶ "pong" (same pid, fully alive) tab_b is simply GONE — not recovered, not relevant to a and c at all

four separate boxes on the OS process table — one disappearing changes nothing about the other three

The Code, Explained

The crash itself is deliberately unglamorous — a real, unhandled exception, exactly like a real bug would produce:

process_isolation.py
if should_crash:
    result_queue.put((tab_id, "crashing", os.getpid()))
    raise RuntimeError(f"simulated renderer crash in tab {tab_id!r}")

And the proof that matters most — not "is it alive," but "can it still do its job":

process_isolation.py
tabs["tab_a"]["cmd_queue"].put("ping")   # sent AFTER tab_b already crashed
tab_id, status, pid = result_queue.get(timeout=10)
# status == "pong", pid == tab_a's ORIGINAL pid

Limits / What You Cannot Do Yet

Can't do yet

  • Automatically restart a crashed tab (real browsers show a "page crashed, reload?" state — not built here)
  • Constrain what a tab process is ALLOWED to do, even before it crashes (Module 25)
  • Real IPC beyond simple queues — no shared rendering surface handoff between processes

Can do now

  • Run each tab as a genuinely separate, independently-verified OS process
  • Prove one tab's real, unhandled crash has zero effect on sibling tabs' continued operation
  • Distinguish "still exists" from "still actually works" in the isolation proof itself

⚠ Getting a blank or broken result?
  • Script hangs indefinitely: on some platforms, `multiprocessing` requires the module-level worker function and the `if __name__ == "__main__":` guard exactly as written — a worker defined as a nested function or lambda will fail to pickle/start correctly.
  • All 4 pids aren't distinct: this would indicate `threading.Thread` got used somewhere instead of `multiprocessing.Process` — threads share their parent's pid entirely.

Brain Exercise

🧠 Think before you reveal

If this module used `threading.Thread` instead of `multiprocessing.Process` for the exact same test, what would actually happen when `tab_b`'s thread raised its unhandled `RuntimeError`? Would `tab_a` and `tab_c` still respond to a ping afterward?

Reveal the answer

An unhandled exception in a `threading.Thread`'s target function doesn't crash the whole process, and by default Python simply prints the traceback and lets that one thread quietly stop — so in THIS specific narrow scenario, `tab_a` and `tab_c` (different threads, still running) might well still respond, making the test LOOK like it passed. That's precisely what makes this comparison worth thinking through: the observable result in this one clean test case can look similar between threads and processes, which is exactly how "we use threads for tabs" mistakes survive code review — until a REAL crash (a genuine segfault, a native-code memory corruption bug, a stack overflow) hits, which in a threaded model can corrupt the WHOLE process's memory, taking every "isolated" thread down with it. `multiprocessing` closes that gap categorically, at the OS level, rather than only for the specific class of crash (a clean Python exception) this test happens to simulate.

There Are No Dumb Questions

Is this really how Chromium/Firefox isolate tabs?
The core mechanism — genuinely separate OS processes, one crash unable to directly corrupt another's memory — is real and matches how modern browsers work. Real browsers add real complexity on top: a shared "browser process" coordinates many "renderer processes," often with more than one tab per renderer process depending on site-isolation policy, plus separate processes for GPU work and network requests. This module's one-tab-per-process model is a simplified but structurally honest slice of that bigger picture.
Why use `multiprocessing.Queue` instead of some other communication method?
Because it's the standard, safe way to pass data between genuinely separate OS processes in Python — under the hood it handles the real OS-level pipe/socket plumbing and serialization (pickling) needed to get a Python object from one process's memory into another's, which is exactly the kind of "OS-mediated channel" prereqs/processes_and_threads.html describes as the only way separate processes can communicate at all.
Does surviving a crash mean tab_a and tab_c are fully "safe" in every sense?
No — this module proves memory-corruption/crash isolation specifically, which is real and valuable, but says nothing about what a tab's process is ALLOWED to do while it's running normally (read arbitrary files? make arbitrary network requests?). That's a completely different, equally important question — and it's exactly what Module 25 addresses next.

What's Next

Process isolation stops a crash from spreading. It does nothing to stop a tab's process from doing something it shouldn't while it's perfectly healthy and running normally — reading a file it has no business reading, for instance. Module 25, this course's bonus module, builds the piece that constrains that: a policy-checked broker a renderer process must go through for anything privileged, instead of being trusted directly.
