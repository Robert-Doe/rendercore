The Big Analogy

🍽️ The Restaurant, continued

The prep cook (Module 5) already split the packing slip into individual instructions. Now someone has to actually stack the trays: this bowl of sauce goes inside that tray of vegetables, which goes inside the main crate. And real packing slips are sloppy — a line might say "start a new tray" without ever saying "that tray is done." A good prep cook doesn't halt the whole kitchen over that; they know the sane, boring rule: a new tray of the same kind means the last one is implicitly done. That's this module's whole job, formalized.

What Happens, Step by Step

  1. Maintain an open-elements stack, starting with one synthetic #document root that's always there.
  2. On a start tag: if it's one that implicitly closes whatever's currently on top of the stack (like a new <p> closing an open <p>), pop that first. Then create the element, attach it as a child of whatever's now on top, and push it — unless it's a void element like <br>, which never goes on the stack at all.
  3. On an end tag: search the stack, top-down, for a matching open element. If found, pop it AND everything above it (closing any unclosed tags that got left open inside it). If not found, ignore the end tag entirely.
  4. On text or a comment: attach it as a child of whatever's on top of the stack right now.
  5. At the end of input, whatever's still on the stack just... stays open. The tree is already correctly nested, because nesting was built the moment each start tag was seen — never deferred.

A Map of the Open-Elements Stack

input: <ul><li>A<li>B</ul> token stack (top on the right) tree so far ------ ------------------------ ----------- StartTag ul [#document, ul] #document > ul StartTag li [#document, ul, li] > ul > li Text "A" > "A" StartTag li auto-close: pop li (top==li match) [#document, ul] [#document, ul, li] > ul > li(2) Text "B" > "B" EndTag ul pop li AND ul (match found at ul, everything above it closes too) [#document]

the stack is the live memory of "what's currently open" — the tree is what's left behind as things close

The Code, Explained

The auto-close check is one `if`, and it's exactly where this module's named simplification lives:

dom_tree_builder.py
closers = AUTO_CLOSE_ON_TOP.get(tok.name)
if closers and len(stack) > 1 and stack[-1].tag in closers:
    stack.pop()
    top = stack[-1]

It only ever looks at stack[-1] — the very top. A real browser's rule can look further up the stack for a boundary element. See DECISIONS.md for exactly which real-world HTML this simplification gets wrong (rare) versus right (the common case).

And the line that makes malformed HTML survivable at all:

dom_tree_builder.py
if match_idx is not None:
    del stack[match_idx:]

Deleting from the match to the end of the stack — not just deleting the one matched entry — is what correctly closes any tags that got left open inside the one that just closed. Without this, a single unclosed <i> inside a properly closed <b> would corrupt the stack for the rest of the document.

Limits / What You Cannot Do Yet

Can't do yet

  • Reopen a formatting element after a misnested close (the real "adoption agency algorithm") — Case 5 in the run below shows exactly where this diverges from a real browser
  • Boundary-aware auto-closing (only checks the immediate stack top)
  • Any style or layout information — this is structure only

Can do now

  • Build a correctly nested tree from well-formed HTML
  • Auto-close common unclosed tags (<p>, <li>, table cells)
  • Correctly handle void elements and stray end tags
  • Produce a valid tree even when input is truncated mid-tag

⚠ Getting a blank or broken result?
  • Every element ends up nested under one giant root with no siblings: check that end tags are actually popping the stack — a missing del stack[match_idx:] would leave everything permanently "open."
  • A void element like <br> swallows everything after it: check it's not being pushed onto the stack — see VOID_ELEMENTS.

Brain Exercise

🧠 Think before you reveal

Given AUTO_CLOSE_ON_TOP only checks the very top of the stack, construct a small HTML snippet where a real browser would auto-close a <p>, but this module's simplified check would fail to.

Reveal the answer

Something like <p>One<span>middle<p>Two — if <span> is left unclosed, it ends up on top of the stack when the second <p> arrives, so stack[-1].tag in closers checks "span" in {"p"}, which is false — no auto-close happens, and the second <p> gets incorrectly nested inside the first one (inside the still-open <span>) instead of becoming its sibling. A real browser's implied-end-tag algorithm would still find and close the ancestor <p> here. This is exactly the gap named in DECISIONS.md's entry on `AUTO_CLOSE_ON_TOP` — real, but affects a narrower slice of real-world HTML than it might first seem, since `` left open across a paragraph boundary is itself unusual.

There Are No Dumb Questions

Why doesn't a stray, unmatched end tag (like a lone </div> with nothing open) crash or raise an error?
Because that's not a hypothetical edge case — it's genuinely common in real-world HTML (often from broken templating systems), and the spec explicitly defines "ignore it" as the correct behavior, not an error condition. A browser that halted on this would be unable to render a large fraction of the real web.
Is Case 5's behavior actually "wrong," or just different from what a browser does?
It's a real, acknowledged limitation, not a bug in the sense Module 5's text-ordering issue was. The tree this module produces for that input is internally consistent and doesn't crash — it just doesn't match what a real browser's rendering would look like, because we don't implement the adoption agency algorithm. DECISIONS.md calls this out by name specifically so it's understood as a scoped-out feature, not an oversight.
Why is there a synthetic #document root instead of just returning a list of top-level nodes?
Because every later module (cascade, layout) wants to walk "the tree" starting from one node, recursively (see trees & recursion) — a list of top-level nodes would mean every one of those modules has to special-case "the top level," instead of just recursing from one root like every other level.
