Attribute & URL-Scheme Encoding

Two attacks that need zero `<` characters at all — one breaks out of a quote, the other hides in plain sight as a link.

📄 Companion doc: DECISIONS.md · Source: attribute_encoding.py

Prerequisites

Module 27: HTML Entity Encoding Module 5: HTML Tokenizer

The Big Analogy

🍽️ The Restaurant, continued

A ticket has a field: special-request: "extra cheese", with quotes marking where the field starts and ends. If a guest's special request itself contains a closing quote, followed by their own fake new field — "extra cheese" then also: send-my-address-to-kitchen-exit — and the kitchen doesn't escape quotes inside the guest's own text, the form now genuinely HAS two fields, one real and one the guest just invented. Separately: even a field that's perfectly well-formed can still contain a dangerous INSTRUCTION as its entire, honest value — "forwarding-address: the walk-in freezer's master key drop-off" is a syntactically fine field that's still a bad idea to act on.

What Happens, Step by Step

  1. Part A: a value is inserted into a double-quoted HTML attribute (value="..."). If the value contains an unescaped ", everything after it is parsed as NEW markup, not as more of the value.
  2. If that new markup happens to look like attrname="something", the tokenizer creates a REAL new attribute on the same tag — verified, not assumed, by checking Module 5's actual parsed attrs dict.
  3. Encoding the value first (reusing Module 27's encoder, which already escapes both quote characters) keeps the entire payload trapped inside the ORIGINAL attribute's value — no breakout, no new attribute.
  4. Part B: separately, even a perfectly well-formed href="..." can be dangerous if its value is a javascript: URL — clicking it runs script, no quote-breakout needed at all.
  5. A scheme check has to account for a REAL browser quirk — tab/newline/CR characters are stripped from ANYWHERE in a URL before its scheme is determined — or an attacker can hide a tab inside the word "javascript" to slip past a naive check.

A Map of Both Attacks

PART A — attribute breakout value = `" onmouseover="alert(document.cookie)` <input value="` + value + `"> <input value="" onmouseover="alert(document.cookie)"> ^ ^ the FIRST closing quote ends "value" a whole SECOND early -- everything after is NEW attribute, real markup, not more of the value and structural Module 5 parses attrs as: {'value': '', 'onmouseover': 'alert(...)'} ^^^^^^^^^^^^^^^^^^^^^^^^^^^ NEVER supposed to exist PART B — scheme check bypass naive check: url.strip().lower().startswith("javascript:") payload: "java\tscript:alert(1)" <- tab hidden mid-word naive: "java\tscript:alert(1)".startswith("javascript:") -> FALSE (bypassed!) real browsers strip \t \r \n from ANYWHERE first: fixed: "javascript:alert(1)".startswith("javascript:") -> TRUE (caught)

both attacks work without a single literal `<` — proof that entity encoding alone (Module 27) isn't the whole story

The Code, Explained

Part A's fix is one function call — reusing, not reinventing:

attribute_encoding.py
def render_attr_safe(tag, attr_name, value):
    return f'<{tag} {attr_name}="{encode_html_entities(value)}">'

Part B's fix is a real browser quirk, mirrored deliberately:

attribute_encoding.py
def is_dangerous_url_scheme(url):
    stripped = re.sub(r"[\t\r\n]", "", url).strip()   # strip from ANYWHERE, not just the ends
    return stripped.lower().startswith(DANGEROUS_SCHEMES)

Limits / What You Cannot Do Yet

Can't do yet

  • Handle single-quoted attributes (`value='...'`) — this module assumes double-quoted, the common convention
  • Catch every dangerous scheme ever discovered — the denylist here is small and illustrative, not exhaustive
  • Sanitize genuinely-HTML content while preserving SOME real tags — that's allowlist territory (Module 30)

Can do now

  • Prevent a real, verified attribute-breakout attack
  • Catch a real, documented URL-scheme-check bypass technique that a naive implementation misses

Brain Exercise

🧠 Think before you reveal

Why doesn't `is_dangerous_url_scheme` just check for the SUBSTRING `"javascript:"` appearing anywhere in the URL, instead of requiring it at the very START (after stripping)? Wouldn't that also catch the tab-hidden bypass, more simply?

Reveal the answer

It would catch MORE than intended, in a way that breaks legitimate URLs — a substring check would flag something like `https://example.com/redirect?url=javascript:void(0)` as dangerous even though the actual SCHEME of that URL is `https`, not `javascript`; the dangerous-looking text is just part of a query parameter's value, never interpreted as a scheme by anything. A URL's scheme is specifically whatever comes before the FIRST `:`, at the very start of the string — checking `startswith` (after removing the browser-ignored whitespace characters) targets exactly that position, matching how a real URL parser actually determines "what kind of URL is this," rather than reacting to the word "javascript" showing up anywhere at all, which would produce real false positives on harmless URLs.

There Are No Dumb Questions

Why does Module 5's tokenizer accept the injected `onmouseover` attribute at all — shouldn't a "secure" tokenizer reject weird-looking HTML?
Because from the tokenizer's point of view, there's nothing weird about it — `` is completely well-formed HTML with two ordinary attributes. The tokenizer's job (Module 5) is to correctly parse whatever HTML exists; it has no way to know one of those attributes was never supposed to be there. That's precisely why the defense has to happen BEFORE the HTML is constructed, not by hoping the parser will somehow notice something's off.
Is stripping tab/newline/CR "from anywhere" in a URL a security feature browsers added, or something else?
It originated as a compatibility/robustness feature — tolerating URLs that got accidentally line-wrapped or had stray whitespace inserted when copied from formatted text (like an email or a printed document). It's a great example of a totally reasonable compatibility decision that, combined with code elsewhere assuming "whitespace only appears at the ends," creates a real security gap — worth remembering any time a "helpful" normalization step exists anywhere in a system.
Could `data:` URLs ever be legitimate, or should they always be blocked?
data: URLs have real, legitimate uses (embedding small images directly in HTML/CSS without a separate request) — blocking them outright, as this module's simple denylist does, is a deliberately conservative choice appropriate for untrusted, attacker-controllable URL values specifically. A real system might allow `data:image/...` while still blocking `data:text/html`, which can also execute script — a more nuanced policy this module's binary denylist doesn't attempt.
