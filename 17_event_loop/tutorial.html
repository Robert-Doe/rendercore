The Event Loop

A browser is single-threaded on purpose. This module is the entire mechanism that makes that safe instead of limiting.

📄 Companion doc: DECISIONS.md · Source: event_loop.py

Prerequisites

Event-Driven Programming

The Big Analogy

🍽️ The Restaurant, continued

The head waiter (introduced in Module 0) handles exactly one request at a time, fully, before looking at the next one — even if three more requests arrive while they're mid-task. A request that arrives while the waiter is already helping someone doesn't interrupt them; it joins the back of a mental list and waits its turn. This isn't the waiter being slow — it's the ONLY way to guarantee that if the waiter is halfway through updating table 5's order, nobody else ever sees that order in a half-updated state.

What Happens, Step by Step

  1. Something happens — a click, a script finishing, a timer firing — and gets post()-ed onto the queue. Nothing runs yet; it just waits its turn.
  2. The loop checks: is the queue non-empty? If so, pop the FRONT item.
  3. Run that task — a plain, synchronous function call. The loop does nothing else until this call returns.
  4. If that task posts new work (e.g. a click handler that starts a fetch, which will post another task when it resolves), the new work goes to the BACK of the queue — never cutting ahead of anything already waiting.
  5. Repeat, forever (or, in this module's own test harness only, until a safety cap is hit — see section 05).

A Map of One Loop Iteration

queue (front -> back): [A, B, C] iteration: pop "A" -> queue is now [B, C] run A() to completion -- nothing else happens while this runs (if A calls post("D", ...) mid-run, queue becomes [B, C, D]) loop checks queue again iteration: pop "B" -> queue is now [C, D] run B() to completion ... RESULT: run order is always A, B, C, D — new work never jumps the line

the loop only ever has ONE question to answer: is the queue empty yet?

The Code, Explained

The entire loop, guarantees and all, is five lines:

event_loop.py
while self.queue and iterations < max_iterations:
    label, task, args = self.queue.popleft()
    self.run_log.append(label)
    task(*args)              # <- runs to completion before the loop continues
    iterations += 1

Nothing about this LOOKS special — that's the point. The guarantee this module proves doesn't come from clever synchronization code; it comes from the ABSENCE of anything that could interrupt task(*args) once it starts. No threads, no async scheduling, no signal handlers — just an ordinary function call that the loop waits on before moving forward.

Limits / What You Cannot Do Yet

Can't do yet

  • Real timers (setTimeout) — this module only proves FIFO ordering, not delayed scheduling
  • Anything to actually PUT in the queue that does something useful — no JS engine exists yet
  • Protection from a runaway task — a real event loop has no `max_iterations` safety net; this module's does, but only for its own automated test

Can do now

  • Guarantee strict FIFO task ordering
  • Guarantee a task posted mid-run never jumps the queue
  • Guarantee no task ever observes another task's partially-applied changes

⚠ Getting a blank or broken result?
  • Case 2 shows D running right after B, not after C: check `post()` always appends — an implementation that inserted at some other position (or ran newly-posted tasks immediately) would break this exact guarantee.
  • Loop never terminates in your own experiments: that's expected if a task keeps reposting itself — this module's `max_iterations` guard exists exactly to keep this specific demo bounded; remove it and a genuinely infinite handler would hang forever, matching real behavior.

Brain Exercise

🧠 Think before you reveal

Case 4 posts tasks in the order: set-a, render-1, set-b, render-2. If a browser instead ran set-a and set-b BACK TO BACK before either render ran — same total work, different order — what would the `render_snapshots` list look like, and would that still be "correct" behavior for an event loop?

Reveal the answer

If both `set-a` and `set-b` ran before any render, `dom["text"]` would be `"B"` by the time EITHER render task got to look at it — so `render_snapshots` would come out as `['B', 'B']`, not `['A', 'B']`. And yes, that would still be entirely correct event-loop behavior — the loop only guarantees the ORDER TASKS WERE POSTED IN is the order they run in; it makes no promise about which specific tasks a caller chooses to post, or in what sequence. This module's Case 4 result (`['A', 'B']`) is a direct consequence of the SPECIFIC order the demo code posted tasks in, not a property of the event loop enforcing some "give every render a turn" fairness rule — the loop has no concept of fairness at all, only strict FIFO.

There Are No Dumb Questions

Is this really how a real browser's event loop works, or a big simplification?
The core mechanism — a queue, popped one at a time, each task run to completion — is genuinely how it works. Real browsers add real complexity on top: separate "macrotask" and "microtask" queues with different draining rules, rendering opportunities interleaved at specific points, and timers that need real wall-clock scheduling. This module's `EventLoop` is the honest foundation those additions sit on top of, not a fake stand-in for it.
Why does this module matter for a "browser" course — isn't this just generic concurrency plumbing?
Because it's the specific mechanism that makes Modules 19 and 20 safe. Once script can mutate the DOM (Module 19), something has to guarantee the render pipeline (Modules 10-16, already built) never gets asked to lay out or paint a tree that's halfway through being changed. That guarantee isn't layout code's job — it's THIS module's job, proven here before either of those modules exists.
What actually happens if a task raises an exception?
In this module's current code, an unhandled exception inside `task(*args)` would propagate up and crash `run_until_empty()` entirely, stopping the whole loop — every remaining queued task, including unrelated ones, would never run. Real browsers handle this differently (an error in one event handler is caught and reported without killing the entire page), which this module doesn't implement — a real, honest gap worth knowing before relying on this code for anything beyond its own demonstrations.
