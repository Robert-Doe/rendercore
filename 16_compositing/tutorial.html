The Big Analogy

🍽️ The Restaurant, continued

The expo checklist was correct (Module 14). The plating staff followed it exactly, item by item (Module 15). But nobody has actually looked at the finished plate yet to confirm the sauce swirl is genuinely visible on top of the garnish, and not secretly hidden underneath it because someone plated in the wrong physical order despite having the right checklist. This module is a food photographer standing over the table, checking the ACTUAL PLATE — not the checklist, not the plating staff's individual movements — to confirm what a diner would really see.

What Happens, Step by Step

  1. Build a scene where two boxes genuinely overlap in real pixel space, deliberately arranged so DOM order and z-index order disagree about which should be visually on top.
  2. Generate the display list (Module 14) and rasterize it onto a real canvas (Module 15) — same pipeline as before, nothing new here.
  3. Pick a real (x, y) coordinate that falls inside BOTH boxes' overlapping region.
  4. Ask Tk directly — not the display list, not the original scene data — what's actually visible at that exact point, using canvas.find_overlapping().
  5. Confirm the TOPMOST item Tk reports is the one z-index says should win — even though it's the one DOM order says should have been painted first (and therefore end up on the bottom).

A Map of the Adversarial Scene

children list order: [first_in_dom (RED, z=5), second_in_dom (BLUE, z=1)] DOM-order-only painting (WRONG, if this module's earlier steps had a hidden bug) would paint RED first, then BLUE on top: overlap region would show BLUE on top <- WRONG, contradicts z-index Actual paint order (Module 13's rule: z-index first, DOM order only breaks ties) paints BLUE first (z=1), then RED on top (z=5): overlap region shows RED on top <- CORRECT overlap region: x:[50,100] y:[50,100] test point: (75, 75) <- solidly inside BOTH boxes canvas.find_overlapping(75,75,75,75) -> (blue_id, red_id) ^^^^^^^ LAST = topmost = visible

the test only means something because DOM order and z-index order were made to disagree on purpose

The Code, Explained

The check that makes this module different from every earlier one — it asks Tk, not the code that produced the scene:

compositing.py
stack_at_point = canvas.find_overlapping(*overlap_point, *overlap_point)
topmost_item = stack_at_point[-1]                     # bottom-to-top order
topmost_color = canvas.itemcget(topmost_item, "fill")

find_overlapping is a real Tk query against the actual rendered canvas state — it has no idea a "z-index" or a "display list" ever existed. If every module before this one had a hidden bug that silently discarded paint order somewhere between the display list and the final canvas, THIS is the check that would catch it, because it never trusts the pipeline's own claim of correctness — it asks the rendering surface directly.

Limits / What You Cannot Do Yet

Can't do yet

  • Real GPU-backed layers or parallel compositing — everything is one 2D Tk canvas
  • Nested stacking contexts (inherited from Module 13's own scope)
  • Opacity/blending between overlapping semi-transparent elements

Can do now

  • Verify, at the pixel level, that stacking order is visually correct — not just structurally correct as data
  • Catch a whole category of bug that Modules 14 and 15's own checks structurally cannot catch

⚠ Getting a blank or broken result?
  • Topmost color comes back blue instead of red: this is exactly the bug this module exists to catch — check that `rasterize()` (Module 15) iterates the display list in the order given, and that the display list itself (Module 14) actually called Module 13's `paint_order()` rather than just using DOM order.
  • find_overlapping returns only one item: your test point may have landed outside the actual overlap region — recompute it from both boxes' real coordinates.

Brain Exercise

🧠 Think before you reveal

Why couldn't Module 15's own checks — which DID verify each item's exact coordinates and colors — have caught a "paints in DOM order instead of paint order" bug, even though that's clearly a real, serious rendering bug?

Reveal the answer

Because Module 15 checked each item IN ISOLATION — "does this specific canvas item have the color and coordinates its command specified" — never "given everything else on the canvas, what's actually visible at this point." A DOM-order painting bug wouldn't change any individual item's color or coordinates at all; it would only change the ORDER in which otherwise-correct items got drawn, which only becomes observable once you ask about the relationship BETWEEN overlapping items — exactly the question `find_overlapping` answers and individual-item checks structurally cannot. This is a general lesson worth keeping past this course: testing that each piece is individually correct is necessary, but it's not the same claim as testing that the assembled whole is correct.

There Are No Dumb Questions

Is this really "compositing," or is it just a more thorough test of what Module 15 already does?
Both, honestly — and that's named directly in DECISIONS.md. Real browser compositing (combining separately-rendered layers, often on the GPU, into one final frame) is more architecturally involved than what this module does. But the CONCEPT compositing is responsible for — "what does the assembled, overlapping result actually look like, not just what does each piece look like alone" — is genuinely what this module verifies, using the single-surface tools this course has available.
Why does the module deliberately construct a scene where the "wrong" answer and the "right" answer would look different, instead of using a more natural-looking test page?
Because a test where the correct implementation and a broken one would produce the SAME result can't actually verify anything — it would pass whether or not the code under test was right. Adversarially designing the DOM order and z-index order to disagree is what makes "the check passed" mean something.
This closes Track 1 — what's actually true about the engine at this exact point?
A URL can go in one end (Module 2), real bytes come back over a real network connection, encrypted if needed (Modules 1, 3, 4), get parsed into a real DOM and real computed styles (Modules 5-9), get laid out into real geometry including text wrapping and flex distribution (Modules 10-13), get flattened into an ordered display list (Module 14), and get rendered onto a real canvas with pixel-verified correct stacking (Modules 15-16). It's static — nothing can change after the first render — but every piece of that pipeline is real, running code, not a description of one.
