TLS via Socket Wrapping

HTTPS isn't a different protocol from HTTP. It's the exact same protocol, run over a sealed envelope instead of an open one.

📄 Companion doc: DECISIONS.md · Source: https_client.py

Prerequisites

Module 1: Raw TCP Socket Module 3: HTTP/1.1 From Scratch

The Big Analogy

🍽️ The Restaurant, continued

The runner's route to the warehouse hasn't changed. The order slip hasn't changed — same handwriting, same format, same words. The only difference is: before handing the slip over, the runner now locks it inside a tamper-evident courier bag, and first checks the warehouse's ID badge against a list of badges the runner's own head office actually trusts — and checks that the name on the badge matches the warehouse the runner was told to visit. If the badge is expired, or belongs to a different warehouse entirely, the runner refuses to hand anything over, full stop.

Nobody at the warehouse counter, and nobody reading the slip once it's delivered, has to know any of this happened. The order-taking and order-reading logic (Module 3) is completely unaware that a courier bag and an ID check now exist.

What Happens, Step by Step

  1. Open a plain TCP connection exactly like Module 1, to port 443 instead of 80.
  2. ssl.create_default_context() loads the OS's list of trusted certificate authorities.
  3. context.wrap_socket(raw_sock, server_hostname=host) performs the TLS handshake: the server presents its certificate, the context checks it chains to a trusted authority AND covers the requested hostname, and (if both pass) a shared encryption key is negotiated.
  4. If either check fails, wrap_socket() raises ssl.SSLCertVerificationError and no HTTP request is ever sent.
  5. If it succeeds, the returned SSLSocket is handed straight to Module 3's format_request() and parse_response() — which have no idea, and don't need to know, that encryption is involved.

A Map of the Layers

Module 3's code: format_request() ---sendall---> parse_response() | ^ v | This module's code: sock.sendall(bytes) sock.recv(n) | ^ | <-- SSLSocket: encrypts/decrypts transparently --> v | Module 1's code: raw TCP byte stream <===== the network =====> Everything ABOVE the SSLSocket line is identical whether or not TLS is used. Everything BELOW it is Module 1, completely unaware TLS exists. TLS lives entirely IN BETWEEN — a wrapper, not a rewrite.

TLS is a socket wrapper, not a parallel protocol stack

The Code, Explained

The entire module's new logic is four lines:

https_client.py
raw_sock = open_connection(host, port, timeout=timeout)   # Module 1, unchanged
context = ssl.create_default_context()
tls_sock = context.wrap_socket(raw_sock, server_hostname=host)
return tls_sock

create_default_context() — not a bare, unverified socket wrap — is the safety-critical choice here. Older code that skips it and calls a low-level wrap function directly can end up with certificate verification silently disabled, which looks like working HTTPS (the page loads!) while providing none of its security guarantees. See DECISIONS.md for why this is called out as a convention worth explaining, not a default worth assuming.

And the proof that nothing downstream changed:

Limits / What You Cannot Do Yet

Can't do yet

  • Implement TLS itself — the cryptography is entirely `ssl`/OpenSSL's job (see DECISIONS.md)
  • Pin a specific certificate or handle client-certificate auth
  • Inspect or override which CAs are trusted (uses the OS's default trust store as-is)

Can do now

  • Fetch any real HTTPS page with the identical parsing logic built in Module 3
  • Prove, with a real failing connection, that certificate chain validation is actually active
  • Prove, with a real failing connection, that hostname verification is actually active

⚠ Getting a blank or broken result?
  • Part 1 fails with a verification error on a real site: your system's CA trust store may be outdated or corrupted — this is worth investigating for real (it's exactly the failure mode that protects you from a genuine attack), not silently working around.
  • Parts 2/3 "succeed" instead of failing: something in your network path (a corporate TLS-inspecting proxy) may be re-signing certificates with its own trusted root — check whether your organization operates one.
  • socket.timeout connecting to badssl.com: some networks block it specifically as a test/security site — try from an unrestricted connection.

Brain Exercise

🧠 Think before you reveal

If `server_hostname` were left out of `wrap_socket()` entirely — socket wrapped, but with no hostname stated — would `create_default_context()`'s verification still meaningfully protect you?

Reveal the answer

Not fully. Chain validation (is this certificate signed by a trusted authority?) can still run without knowing the intended hostname — but hostname verification (does this certificate actually belong to the site I meant to visit?) cannot happen at all without it, because there's nothing to compare the certificate's names against. A certificate can be perfectly validly signed by a trusted CA and still belong to a completely different, unrelated domain — chain validity says "this certificate is genuine," not "this certificate is for the site you think it's for." That second, distinct guarantee is exactly what Part 3's `wrong.host.badssl.com` test is designed to catch, and it depends entirely on `server_hostname` being passed.

There Are No Dumb Questions

If TLS is "just" a socket wrapper, why does HTTPS use a different port (443) than HTTP (80)?
Historical convention, not a technical requirement of TLS itself — a server could be configured to speak TLS on any port. Port 443 was registered early on specifically for "HTTP over TLS," and universal adoption of that convention is what lets a client assume `https://` means "try port 443" without any negotiation, the same way `DEFAULT_PORTS` in Module 2 encodes it.
Does `parse_response()` need to know it's reading from an `SSLSocket` instead of a plain one?
No — and that's the module's central point. `SSLSocket.recv()` has the identical method signature and behavior contract as `socket.socket.recv()`: it returns decrypted plaintext bytes, blocks the same way, and signals connection-closed with `b""` the same way. Every function in Module 3 that calls `sock.recv()` or `sock.sendall()` works unmodified against either socket type.
Is it actually dangerous to skip certificate verification, or is that overly cautious for a learning project?
It's genuinely dangerous, not just overly cautious, which is why this module includes Parts 2 and 3 instead of stopping at Part 1. Skipping verification means any attacker capable of intercepting your network traffic (a hostile Wi-Fi network, a compromised router) can present any certificate at all and your client will accept it — defeating the entire purpose of encryption, since the attacker can decrypt, read, and even modify traffic while your client shows no error.
