Cookies & Storage

The web is stateless by design (Module 3). Cookies are the specific, bounded exception a server can ask the client to remember for it.

The Big Analogy

🍽️ The Restaurant, continued

The restaurant hands returning guests a small numbered claim ticket: "next time you visit, show us this and we'll remember your usual table." The ticket has fine print: which SECTION of the restaurant it's valid for ("front dining room only," or "anywhere") and whether it's honored at all if you show up through the back service entrance instead of the front door (a plain, unencrypted connection vs. a secure one). The restaurant never has to remember you between visits on its own — the GUEST carries the ticket back, every time, and the restaurant just honors whatever it's shown.

What Happens, Step by Step

  1. A response includes one or more Set-Cookie headers. Each is parsed into a name, value, path scope, and whether it requires a secure connection.
  2. The cookie is stored, keyed by which host set it and what path it's scoped to.
  3. On every LATER request to that same host, the jar is asked: which stored cookies apply to THIS specific request path (and connection security)?
  4. Only the matching cookies are joined into one Cookie: header and sent — a cookie scoped to /account is never sent for a request to /.
  5. The jar can be saved to disk and reloaded later, in a completely different object/process, and produce identical results — proving the state genuinely persisted, not just stayed alive in memory.

A Map of Path Scoping

Set-Cookie: session=abc123; Path=/ <- matches EVERYTHING Set-Cookie: pref=dark; Path=/account <- matches /account and deeper only request to "/" -> Cookie: session=abc123 request to "/account" -> Cookie: session=abc123; pref=dark request to "/accounting" -> Cookie: session=abc123 (NOT pref — see section 07) path match rule: request_path == cookie_path OR request_path.startswith(cookie_path + "/")

the trailing "/" in the startswith check is small and load-bearing — see the brain exercise

The Code, Explained

The path-matching guard against a subtle false-positive:

cookies.py
def _path_matches(cookie_path, request_path):
    if request_path == cookie_path:
        return True
    prefix = cookie_path if cookie_path.endswith("/") else cookie_path + "/"
    return request_path.startswith(prefix)

Without the trailing-slash normalization, "/accounting".startswith("/account") is True in plain Python string comparison — which would incorrectly leak an /account-scoped cookie to an entirely different, unrelated path that just happens to share a text prefix.

Verification doesn't trust the client's own claim — it inspects what actually arrived at the server:

cookies.py
server_saw = holder["requests"][1].decode("ascii", errors="replace")
print(f"'session=abc123' in server_saw and 'pref=dark' not in server_saw")

Limits / What You Cannot Do Yet

Can't do yet

  • Domain= subdomain-widening — cookies are scoped to the exact host that set them
  • Expires/Max-Age — no cookie ever expires in this module
  • localStorage/sessionStorage — this module covers cookies only

Can do now

  • Correctly parse and scope real Set-Cookie headers by path
  • Correctly withhold path-mismatched and (if applicable) insecure-connection cookies
  • Prove persistence across a genuine object/process boundary, not just within one run

⚠ Getting a blank or broken result?
  • Cookies leak to the wrong path: check `_path_matches` includes the trailing-slash guard — without it, path prefixes can false-match.
  • Reloaded jar produces different output than the original: check `save()`/`load()` round-trip every field on `Cookie` (name, value, domain, path, secure) — dropping one silently changes matching behavior after reload.

Brain Exercise

🧠 Think before you reveal

If `_path_matches` used `request_path.startswith(cookie_path)` directly — no trailing-slash normalization — would a cookie scoped to `Path=/account` be sent on a request to `/accounting`? Is that a theoretical concern or a realistic one?

Reveal the answer

Yes, it would leak — "/accounting".startswith("/account") evaluates to True in Python, since `/accounting` genuinely does begin with the six characters `/account`. And it's a realistic concern, not a manufactured edge case: real sites commonly have paths like /user and /users, or /api and /apidocs, where an unguarded prefix check would leak a cookie meant for one path scope into requests for a completely different, unrelated section of the site. This is exactly the class of bug RFC 6265's actual path-matching algorithm is written carefully enough to avoid, and exactly why `_path_matches` isn't just `request_path.startswith(cookie_path)`.

There Are No Dumb Questions

Why does this module use a local hand-rolled server instead of a real cookie-setting website?
Determinism, the same reasoning as Module 3's local chunked-encoding test. A public test endpoint can go down, change its behavior, or rate-limit — and this module's whole point is testing precise path-scoping logic, which needs a server that behaves EXACTLY the same way every single run.
Is checking `Secure` at request-time instead of storage-time a meaningful difference?
Yes — it means the exact same stored cookie can correctly be included or excluded depending on how THIS SPECIFIC request is being made, without needing two separate jars or a resync step. It also matches how the real security property actually works: `Secure` isn't about where a cookie lives, it's about what kind of connection it's allowed to travel over.
Why prove persistence with `is not` (object identity) again, the same technique Module 20 used?
For the same reason: it's the only way to rule out an accidental false-positive where the "reloaded" jar is secretly still the original object (e.g., a `load()` implementation that forgot to actually create a new instance). Confirming both that the VALUES match and that the OBJECT is different together prove real serialization happened, not that nothing was ever separated in the first place.
